# 精简模式 - 技能文档精简方法论

## 核心定位

在**严格保持技能功能完整性**的前提下，通过删除冗余、压缩表述、提取详细内容，显著减少技能文档的长度和 token 消耗，提升加载效率和可读性。

精简的目标是让技能表达直达本质，抓住重点和关键信息，删除不必要的冗余说明，同时不能削减原有的技能能力。

> 本文件是 [rewrite-workflow.md](rewrite-workflow.md)「针对性重写执行」中 **表达精简维度的展开**，以及 `--simplify` 入口所用的四档策略细节，不是一条独立工作流。诊断 → 选择 → 执行 → 验证的骨架仍以 rewrite-workflow.md 为准。

## 精简三原则

1. **表达直达本质**：用最少的词传达完整的意图，避免修饰性、解释性冗余
2. **保持功能完整**：所有功能点、约束、工作流逻辑必须完整保留
3. **用户决定边界**：可能影响行为的精简点，必须标识并由用户确认

## 精简点分类

精简操作按风险级别分为三类：

| 类别 | 定义 | 示例 | 风险 |
|------|------|------|------|
| **安全精简** | 删除后不影响 Claude 理解和执行的冗余 | 重复表述、同义解释、显而易见的注释、修饰性冗余 | 无 |
| **结构精简** | 通过重组减少正文长度，不改变内容 | 提取到 references、合并同构段落、精选示例 | 低 |
| **激进精简** | 可能影响 Claude 理解或行为的简化 | 删除边缘示例、简化约束表述、合并相似功能描述 | 中-高 |

## 诊断检查清单

### 专项：精简判断标准

按风险级别找可精简点。下面是判断标准，不是勾选清单——逐条问"这里有没有这种情况"，有则记录位置。

**安全精简（删除后不影响理解与执行）：**

- 同一事实在多处用不同措辞重复说了几遍 → 保留最清楚的一次
- 对目标读者不言自明的解释 → 目标读者是能读懂技能其余部分的模型，不需要基础概念铺垫
- 强调词堆砌（"非常""极其""务必"连用）→ 强调词的效力来自稀缺，堆砌等于没有
- 长句里塞了多件事 → 拆成每句一件事。句子长到需要回读才能确定主语指什么，就该拆

**结构精简（重组减少正文长度，不改内容）：**

- 多个示例覆盖同一场景 → 只留最清楚的一个。示例的数量应服务于覆盖独特场景，不服务于凑数
- 详细说明只在一两处被用到，且短到内联不影响正文节奏 → 内联，省掉一次文件读取
- 教学式的因果链条（"因为 A 所以 B，因为 B 所以 C，所以要做 D"）→ 压缩为结论加一句关键理由
- 同一概念存在多种表述 → 统一为一种

**激进精简（可能影响理解或行为）：**

- 示例覆盖的是非典型场景 → 删除会牺牲边缘场景的理解，需用户确认
- 约束带多个边界条件，且边界条件本身可由核心约束推出 → 可简化为核心约束
- 步骤说明的详细程度超出执行所需 → 压缩为要点

**参考刻度**（不是触发条件，是"该停下来看一眼"的提示）：单个主题详细内容超过 300 行、SKILL.md 接近 500 行、单个示例超过 20 行。这三个量模型无法自行标定，所以给刻度；其余判断项模型本就能判断，不设数字。

### 专项：精简额外验证

使用 [rewrite-workflow.md](rewrite-workflow.md)「基线验证和变更总结」中定义的标准基线验证流程，额外增加精简专项检查：

- [ ] 每个约束的边界条件是否仍可被 Claude 理解？
- [ ] 删除的示例是否覆盖了独特场景（若是，需保留或改为一句话说明）？
- [ ] 简化后的表述是否存在歧义？
- [ ] 提取到 references 的内容是否有清晰的引用和阅读时机说明？

## 细粒度精简控制

当用户使用 `--simplify` 快捷入口时，可提供比 `--rewrite` 模式更细粒度的精简控制。

### 诊断输出格式（细粒度）

```markdown
## 精简诊断结果

### 安全精简（共 X 处）
| # | 位置 | 类型 | 当前表述 | 精简后 | 节省 |
|---|------|------|----------|--------|------|
| 1 | L23-25 | 重复表述 | "..." | "..." | 12 词 |

### 结构精简（共 Y 处）
| # | 位置 | 类型 | 当前结构 | 精简方案 | 节省 |
|---|------|------|----------|----------|------|
| 1 | §示例库 | 提取到 references | 正文 80 行示例 | 移至 references/examples.md | ~70 行 |

### 激进精简（共 Z 处）⚠️
| # | 位置 | 类型 | 当前表述 | 精简后 | 风险说明 |
|---|------|------|----------|--------|----------|
| 1 | L89-95 | 简化约束 | "..." | "..." | 删除了边界条件说明 |
```

实际节省在执行后的精简日志里记录（见「注意事项」第 3 条）。诊断阶段不预报总百分比——预报的数字会变成要凑到的目标，反过来影响删改判断。

### 用户确认格式（细粒度）

```markdown
根据精简诊断，发现：
- ✅ **安全精简**：X 处，删除冗余表述，不影响功能
- 🔧 **结构精简**：Y 处，重组内容分层，不改变语义
- ⚠️ **激进精简**：Z 处，简化表述或删除边缘内容，**可能影响边缘场景理解**

**激进精简的风险**：
[具体列举可能影响的场景]

请选择精简策略：
1. **保守**：只执行安全精简与结构精简。只删语义重复和显而易见的解释，不动任何示例和约束表述
2. **平衡**：加上激进项中的表达简化——合并同构表达、压缩步骤说明，但保留全部示例和边界条件说明
3. **激进**：执行全部精简项，包括删除边缘场景示例、简化带边界条件的约束
4. **自定义**：手动选择激进精简项（输入编号，如 `1,3,5`）
```

## 典型精简技巧

### 技巧 1：删除重复表述

**特征**：同一事实在多处用不同措辞重复

**操作**：定位所有重复，保留最清晰的一次，删除其他

**示例**：
```
精简前：技能创建很重要。编写技能时，创建高质量的技能文档非常关键。好的技能文档是成功的基础。
精简后：编写高质量的技能文档是成功的基础。
```

### 技巧 2：压缩过度解释

**特征**：因果链条过长、解释显而易见的内容

**操作**：压缩为核心要点，用括号补充关键理由

**示例**：
```
精简前：在这一步中，你需要做的事情是阅读用户提供的所有相关文件。这很重要，因为只有读完文件，你才能理解上下文。理解上下文之后，你才能正确地执行后续步骤。所以一定要先读文件。
精简后：先读取相关文件以理解上下文，再执行后续步骤。
```

### 技巧 3：简化冗长句式

**特征**：一句话里塞了多件事，或需要回读才能确定主语指什么

**操作**：拆分为多个短句，每句只说一件事；或用列表替代长句

**示例**：
```
精简前：当你在处理用户请求的时候，如果遇到了不太清楚或者不太确定的情况，你应该主动向用户提出问题来澄清你的疑惑，而不是自己猜测用户的意图，因为猜测可能会导致错误的结果。
精简后：遇到不确定的情况时，主动向用户提问澄清，不要猜测意图。
```

### 技巧 4：删除修饰性冗余

**特征**：非常、极其、务必、一定、绝对等强调词堆砌

**操作**：删除修饰词，保留核心动词或名词

**示例**：
```
精简前：你必须非常仔细地、极其认真地检查每一个细节。
精简后：仔细检查每个细节。
```

### 技巧 5：提取示例到 references

**特征**：多个示例覆盖同一场景，或单个示例长到打断正文节奏

**操作**：保留 1-2 个最典型示例在正文，其余移至 references/examples.md

**示例**：
```
精简前（正文 80 行）：
### 示例
示例 1：创建 API 技能 [20 行]
示例 2：创建数据处理技能 [20 行]
示例 3：创建文档生成技能 [20 行]
示例 4：创建测试技能 [20 行]

精简后（正文）：
### 示例
详见 [examples.md](references/examples.md)，包含 API、数据处理、文档生成、测试等 4 类典型场景。
```

### 技巧 6：统一相似表达

**特征**：同一概念用了多种表述（如"子智能体""子 agent""subagent"）

**操作**：选择最简洁的形式，全文统一

**示例**：统一使用"子智能体"，删除其他变体

### 技巧 7：合并同构段落

**特征**：多个段落结构相同，仅参数不同

**操作**：用表格或列表替代重复段落

**示例**：
```
精简前：
对于 JSON 输出：[30 行处理逻辑]
对于 Markdown 输出：[30 行处理逻辑]
对于 HTML 输出：[30 行处理逻辑]

精简后：
| 格式 | 参考文件 | 何时使用 |
|------|---------|---------|
| JSON | [json-output.md](references/json-output.md) | 机器可读输出 |
| Markdown | [md-output.md](references/md-output.md) | 默认人类可读 |
| HTML | [html-output.md](references/html-output.md) | 富文本或可视化 |
```

## 注意事项

1. **保守策略必须零风险**：保守模式下的精简必须完全安全，不影响任何行为
2. **具体定位**：诊断时要给出具体的行号/章节引用，不能凭空断言"太长了"
3. **量化效果**：精简日志要记录节省的行数和 token 数，让用户看到量化效果
4. **尊重用户决策**：激进精简项必须由用户确认，不可擅自执行
5. **基线验证必须严格**：所有功能点、约束、工作流逻辑必须完整保留，不得遗漏

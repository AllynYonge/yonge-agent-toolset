# 分析模式 - 技能质量分析方法论

## 核心定位

对目标技能进行**只读、证据驱动**的质量评估，输出结构化诊断报告。不修改任何文件，仅提供洞察和改进方向建议。

分析模式是技能改进的前置步骤：在用户决定是否重写、优化或改进之前，先了解技能的现状、优劣势和改进空间。

## 分析维度

### 一、战略层（道）- 为什么存在

| 维度 | 分析要点 |
|------|---------|
| **核心价值** | 技能解决了什么 Claude 原生处理不好的问题？独特价值是什么？ |
| **战略定位** | 是控制型（强制一致性）还是探索型（启发创造力）？定位是否清晰？ |
| **触发准确性** | description 是否清楚表达使用场景？是否存在欠触发或误触发风险？ |
| **壁垒思维** | 技能是否构建了难以模仿的价值？还是可以被简单提示词替代？ |

### 二、架构层（法）- 如何组织

| 维度 | 分析要点 |
|------|---------|
| **方法论清晰度** | 技能采用了什么策略、框架或心智模型？是否明确阐述？ |
| **工作流完整性** | 主流程是否完整、清晰、无断点？分支逻辑是否完备？ |
| **资源组织** | SKILL.md vs references/ vs agents/ vs scripts/ 的分工是否合理？ |
| **引用效率** | references/ 是否按需加载？是否存在过度/不足利用？ |
| **子 agent 集成** | 若使用 agents/，交接是否明确？职责是否清晰？ |
| **脚本自动化** | 确定性任务是否正确委托给 scripts/？还是在 SKILL.md 重复编排？ |

### 三、实现层（术）- 具体执行

基于技能编写指南的**八大原则**进行逐项诊断：

| # | 原则 | 评估重点 |
|---|------|---------|
| 1 | **渐进式披露** | SKILL.md 是否控制在 500 行内？详细内容是否正确分层到 references/？ |
| 2 | **扩展性** | 新增功能/格式/模式时是否需要改动核心正文？是否存在写死的同构条目？ |
| 3 | **结构组织规范** | 章节层级是否清晰？导航标记是否完整？是否便于快速定位？ |
| 4 | **指令放置** | 核心约束是否出现在认知优势位置（顶部/底部）？还是迷失在中段？ |
| 5 | **交互引导** | 用户交互路径是否清晰？是否明确「下一步做什么」？ |
| 6 | **重点解释** | WHY（推理）和 WHAT（指令）的比例是否合理？是否过度发号施令？ |
| 7 | **术语一致性** | 核心概念的命名是否统一？是否存在同义词混用？ |
| 8 | **表达精简** | 是否存在冗余表述、重复段落、可合并的同类指令？ |

## 分析工作流

### 步骤 1：基线提取

完整阅读目标技能的 SKILL.md 及所有 references/ 文件，提取并记录：

```markdown
## 功能基线

### 核心意图（道）
[一句话：技能为什么存在？]

### 方法论（法）
[技能采用什么策略、框架或心智模型？]

### 功能清单（术）
1. [功能 1 - 一句话描述]
2. [功能 2 - 一句话描述]
...

### 约束清单
- 正向约束：[必须做什么]
- 负向约束：[不得做什么]

### 工作流逻辑
[主流程简述 + 关键分支]

### 快捷入口
[如果有 --flag 模式，列出所有入口及其用途]

### 资源清单
- references/: [列出所有文件及用途]
- agents/: [列出所有 agent 及职责]
- scripts/: [列出所有脚本及触发时机]
```

### 步骤 2：三层质量诊断

#### 2.1 战略层（道）诊断

针对核心价值、战略定位、触发准确性、壁垒思维四个维度，逐项评估：

```markdown
## 战略层（道）诊断

### 核心价值
- **判定**：[清晰 / 模糊 / 缺失]
- **证据**：[引用 SKILL.md 中相关段落，标注行号或章节]
- **分析**：[这个技能解决的独特问题是什么？若去掉会失去什么？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 战略定位
- **判定**：[控制型 / 探索型 / 混合 / 不明确]
- **证据**：[引用相关段落]
- **分析**：[定位是否与实际指令一致？是否存在定位混乱？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 触发准确性
- **判定**：[精准 / 可能欠触发 / 可能误触发]
- **证据**：[引用 frontmatter description]
- **分析**：[description 是否覆盖所有应触发场景？是否足够主动？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 壁垒思维
- **判定**：[有壁垒 / 弱壁垒 / 无壁垒]
- **证据**：[引用体现方法论独特性的段落]
- **分析**：[这个技能能否被简单提示词替代？独特价值在哪？]
- **严重度**：[高 / 中 / 低 / 无问题]
```

#### 2.2 架构层（法）诊断

针对方法论清晰度、工作流完整性、资源组织、引用效率、子 agent 集成、脚本自动化六个维度：

```markdown
## 架构层（法）诊断

### 方法论清晰度
- **判定**：[清晰 / 隐含 / 缺失]
- **证据**：[引用阐述方法论的段落]
- **分析**：[技能教给 Claude 什么策略或框架？是否显式阐述？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 工作流完整性
- **判定**：[完整 / 有断点 / 分支不全]
- **证据**：[引用工作流相关段落，标注缺失部分]
- **分析**：[主流程是否闭环？边界情况是否处理？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 资源组织
- **判定**：[合理 / 过度拆分 / 拆分不足]
- **证据**：[列出 SKILL.md 行数，references/ 文件清单]
- **分析**：[SKILL.md 是否超 500 行？references/ 是否被正确利用？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 引用效率
- **判定**：[高效 / 过度加载 / 利用不足]
- **证据**：[引用 SKILL.md 中对 references/ 的调用指令]
- **分析**：[是否明确何时阅读？是否存在用不到的大块内容被加载？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 子 agent 集成（若无 agents/ 则跳过）
- **判定**：[清晰 / 职责模糊 / 交接不明]
- **证据**：[引用 agent 调用相关段落]
- **分析**：[每个 agent 的职责是否单一？输入输出是否明确？]
- **严重度**：[高 / 中 / 低 / 无问题]

### 脚本自动化（若无 scripts/ 则跳过）
- **判定**：[充分 / 委托不足 / 过度依赖]
- **证据**：[列出 scripts/ 清单，分析哪些任务应该但未脚本化]
- **分析**：[确定性任务是否正确委托？SKILL.md 是否重复描述脚本逻辑？]
- **严重度**：[高 / 中 / 低 / 无问题]
```

#### 2.3 实现层（术）诊断

基于八大编写原则，逐项检查。使用统一诊断表格：

```markdown
| 2 | 扩展性 | [高/中/低/无] | [具体问题描述] | [SKILL.md §X / Lxxx] | [修复后的预期改善] |
| 3 | 结构组织规范 | [高/中/低/无] | [具体问题描述] | [SKILL.md §X / Lxxx] | [修复后的预期改善] |
| 4 | 指令放置 | [高/中/低/无] | [具体问题描述] | [SKILL.md §X / Lxxx] | [修复后的预期改善] |
| 5 | 交互引导 | [高/中/低/无] | [具体问题描述] | [SKILL.md §X / Lxxx] | [修复后的预期改善] |
```

```markdown
   ...
```

## 分析质量要求

1. **证据驱动**：每个判定必须引用原文作为论据，标注具体位置（章节名 / 行号）
2. **严重度准确**：
   - **高**：严重影响指令遵从率、可维护性或用户体验
   - **中**：有改进空间但不影响核心功能
   - **低**：细微瑕疵，锦上添花
3. **可操作性**：建议必须具体到可执行的改进方向，并关联到现有模式（--rewrite / --simplify / --optimize-desc / --eval）
4. **深度优先**：追求洞察深度而非覆盖广度，抓住本质问题
5. **方法论沉淀**：从每个分析中提炼可推广的设计模式
6. **壁垒思维**：评估技能是否创建了独特的、难以复制的价值
7. **只读承诺**：分析过程**绝不修改任何文件**，纯诊断输出

## 输出规范

分析完成后，输出完整的结构化报告（遵循步骤 4 的报告格式）。

报告用中文输出，所有技术术语保持英文（如 SKILL.md、references/、--rewrite 等）。

**禁止**：
- 未经用户同意直接进入重写/优化流程
- 给出没有原文证据支撑的判断
- 使用「总体来说不错」之类的空话
- 建议用户「根据实际情况决定」（必须给出明确的优先级和下一步建议）

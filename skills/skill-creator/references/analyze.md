# 分析模式 - 技能质量分析方法论

## 核心定位

对目标技能进行**只读、证据驱动**的质量评估，输出结构化诊断报告。不修改任何文件，仅提供洞察和改进方向建议。

分析模式是技能改进的前置步骤：在用户决定是否重写、优化或改进之前，先了解技能的现状、优劣势和改进空间。

## 分析维度

分析沿「道·法·术」三层展开，每层同时识别**优点**和**不足**。下列表格是唯一权威的维度定义——每个维度的「分析要点」既是诊断时的检查清单，也是评价优劣时需要回答的问题。

### 层级对齐原则（贯穿全部分析）

**每一层的不足与改进建议，必须停留在该层自身的抽象高度。** 三层是三种不同的思考距离，混层会让报告失去诊断力：道层的问题被降格成措辞修补，会掩盖"方向错了"；术层的问题被抬成方法论争论，会让本可一行修好的事悬空。

| 层级 | 思考距离 | 改进建议应形如 |
|------|---------|--------------|
| **道** | 退到技能之外看：这个问题是什么，值不值得做，有没有更好的解法 | 重新定位、收窄或扩大边界、拆分/合并技能、改换整体策略、乃至判定"不该做成技能" |
| **法** | 退到指令之外看：能力怎么切分、流程怎么串、资源怎么分工 | 重构工作流、调整模式划分、改变资源分层、引入路由或数据驱动机制 |
| **术** | 贴着文字看：这条指令模型能不能稳定照做 | 补 WHY、改正向表述、加示例或模板、挪动关键约束位置、统一命名 |

**越上层，越要先后退一步再评价。** 分析道层时，先不问"它写得好不好"，而问：用户真正的问题是什么？当前这套解法是不是最短路径？有没有一个完全不同的思路（换载体、换介入时机、借用别的技能、干脆交给 Claude 原生处理）能更好地解决它？只有在确认方向可取之后，才评价它在这个方向上做得如何。若确实存在更优思路，必须写进道层的「不足与改进」，即使这意味着建议重做整个技能——这是分析报告最有价值的产出之一，不要因为结论重就回避。

### 一、战略层（道）- 为什么存在

| 维度 | 分析要点 |
|------|---------|
| **问题本身** | 用户真正要解决的问题是什么（不是技能做什么）？这个问题被表述准确了吗，还是技能在解一个被误设的问题？ |
| **核心价值** | 技能解决了什么 Claude 原生处理不好的问题？独特价值是什么？若去掉会失去什么？ |
| **解法最优性** | 当前解法是通向该问题的最短路径吗？是否存在完全不同的思路更优——换载体（脚本/子智能体/数据驱动）、换介入时机、复用已有技能、拆成多个技能、或干脆交给 Claude 原生处理？ |
| **战略定位** | 是控制型（强制一致性）还是探索型（启发创造力）？定位是否清晰且与实际指令一致？ |
| **触发准确性** | frontmatter description 是否覆盖所有应触发场景且足够主动？是否存在欠触发或误触发风险？ |
| **用户价值闭环** | 技能的输出是否直接服务于用户的终端目标？从触发到交付的路径是否最短且无冗余步骤？用户是否需要额外加工才能使用输出？ |

### 二、架构层（法）- 如何组织

| 维度 | 分析要点 |
|------|---------|
| **方法论清晰度** | 技能采用了什么策略、框架或心智模型？是否显式阐述？ |
| **工作流完整性** | 主流程是否完整闭环、无断点？分支逻辑与边界情况是否完备？ |
| **资源组织** | SKILL.md vs references/ vs agents/ vs scripts/ 的分工是否合理？SKILL.md 是否超 500 行？ |
| **引用效率** | references/ 是否按需加载？是否明确何时阅读？是否存在用不到的大块内容被加载？ |
| **子 agent 集成**（若无 agents/ 则跳过） | 交接是否明确？每个 agent 职责是否单一、输入输出是否清晰？ |
| **脚本自动化**（若无 scripts/ 则跳过） | 确定性任务是否正确委托给 scripts/？SKILL.md 是否重复编排脚本逻辑？ |
| **配置设计**（若技能无持久化配置则跳过） | 配置是否按被读时机切分三层承载位置？优先级链是否单行声明且与实现一致？可变项是否建模成映射？清单是否单一来源？目录、格式与密钥隔离是否符合统一约定？判据以 `references/paradigms/config-paradigm.md` 第一节为唯一权威定义，此处不复述 |

### 三、实现层（术）- 能力实现质量

| 维度 | 分析要点 |
|------|---------|
| **能力完整度** | 承诺的能力是否都有对应实现？是否有空壳功能（描述提到但正文无实质指令）？功能清单与实际覆盖是否一致？ |
| **边界与降级** | 输入异常、信息不足、工具失败时的处理是否完备？是否有明确的降级策略而非静默失败？ |
| **指令可遵从性** | 指令是否清晰到模型能稳定遵从？是否存在歧义、矛盾或过于抽象的要求？（表述方式与位置安排属「文档工程」的重点解释性、指令放置两项，在那里诊断） |
| **输出质量保障** | 输出格式、质量标准、验证机制是否足够？是否有示例或模板帮助模型校准输出？ |
| **文档工程** | MUST 对照 SKILL.md「技能编写指南」章节列出的全部原则逐一检查。该章节是原则清单与判据的唯一来源，此处不复述（避免两处漂移）。诊断粒度与 `rewrite.md` 步骤 2 一致：逐项判定「有问题 / 无问题」，有问题则逐条给出原文位置与预期效果 |

## 分析工作流

### 步骤 1：基线提取

完整阅读目标技能的 SKILL.md 及所有 references/ 文件，提取并记录：

```markdown
## 功能基线

### 核心意图（道）
[一句话：技能为什么存在？]

### 方法论（法）
[技能采用什么策略、框架或心智模型？]

### 功能清单（术）
1. [功能 1 - 一句话描述]
2. [功能 2 - 一句话描述]
...

### 工作流逻辑
[主流程简述 + 关键分支]

### 快捷入口
[如果有 --flag 模式，列出所有入口及其用途]

### 资源清单
- references/: [列出所有文件及用途]
- agents/: [列出所有 agent 及职责]
- scripts/: [列出所有脚本及触发时机]
```

### 步骤 2：三层深度分析

对「分析维度」中定义的每个维度，从原文中寻找证据，**同时识别优点和不足**。

**按道 → 法 → 术的顺序分析，不要跳序。** 上层结论会改变下层的分析意义：若道层判定方向需要调整，法层与术层的诸多细节问题就不再值得逐条打磨，此时应在下层如实标注「若采纳道层建议，本项问题自然消解」，而不是继续堆砌无关紧要的修补建议。

每一层使用相同的报告格式：

```markdown
## [层名]（道/法/术）分析

- **优点：**
  - [分析点：基于原文证据的分析。引用 SKILL.md 章节名或行号]
  - [分析点：...]

- **不足与改进：**

| 不足 | 证据 | 改进方向 |
|------|------|----------|
| [具体问题描述] | [SKILL.md 章节名 / 行号] | [具体可执行的建议] |
| [...] | [...] | [...] |
```

**分析规则**：

- 优点和不足必须引用原文作为论据，标注具体位置（章节名 / 行号）
- 不足后必须紧跟改进方向，不能只指出问题不给建议
- 改进方向要具体到可执行，不能是「建议优化」这类空话
- 某一层没有实质发现时省略该节，不留空表
- 架构层中标注「若无则跳过」的维度，当技能无对应目录时直接省略
- 深度优先于广度：抓住本质问题比逐项打勾更重要
- **改进方向必须与所在层级同高**（见「层级对齐原则」）：道层给方向性建议，法层给结构性建议，术层给文字性建议。若某层的改进方向写出来是另一层的动作，说明问题被归错了层——把它挪到对应层，而不是原地降格

### 步骤 3：可复用方法论提取

识别技能中可推广的设计模式，**按道·法·术分层归置**——每层沉淀的是不同种类的可迁移知识，混在一起会让"定位取舍"和"措辞技巧"等价，失去参考价值：

| 层 | 该层沉淀什么模式 | 举例 |
|----|----------------|------|
| **道** | 定位与取舍模式：如何界定问题边界、如何判断该不该做、如何选择整体策略 | 「控制型 vs 探索型的定位判据」「以用户终端目标反推最短路径」 |
| **法** | 架构与流程模式：能力如何切分、流程如何编排、资源如何分层 | 「维度勾选式诊断-执行骨架」「数据驱动的可插拔变体」 |
| **术** | 指令与表达模式：如何写出模型能稳定遵从的指令 | 「先给 WHY 再给规则」「正向表述替代禁令」 |

```markdown
## 可复用方法论

### 道层：定位与取舍模式

1. **[模式名称]**
   - **适用场景**：[什么类型的技能可以复用这个模式？]
   - **核心机制**：[这个模式的关键设计是什么？]
   - **证据**：[引用技能中体现该模式的段落]
   - **可迁移性**：[如何将这个模式应用到其他技能？]

### 法层：架构与流程模式

1. **[模式名称]**
   - [同上四项]

### 术层：指令与表达模式

1. **[模式名称]**
   - [同上四项]
```

只写真正能迁移到其他技能的模式。多数技能能沉淀一到两条，写不出也可以整节省略。

### 步骤 4：生成结构化报告

下列骨架是组织参考，不是必填模板。哪一层有实质发现就写哪一层，某层没有就整节省略。报告的价值在少数关键洞察，不在结构完整——一份只写透了道层一个方向性问题的报告，比三层各填两行的报告有用。

骨架如下：

```markdown
# 技能分析报告：[技能名称]

## 1. 总体评价
- **一句话亮点**：[最核心的优势]
- **一句话短板**：[最大的改进空间]
- **技能成熟度**：[草稿期 / 可用期 / 成熟期 / 精品期]

---

## 2. 战略层（道）分析
- **优点：**
  - [分析点：基于原文证据]
  - ...

- **不足与改进：**

| 不足 | 证据 | 改进方向 |
|------|------|----------|
| [问题描述] | [章节/行号] | [具体建议] |

---

## 3. 架构层（法）分析
- **优点：**
  - [分析点：基于原文证据]
  - ...

- **不足与改进：**

| 不足 | 证据 | 改进方向 |
|------|------|----------|
| [问题描述] | [章节/行号] | [具体建议] |

---

## 4. 实现层（术）分析
- **优点：**
  - [分析点：基于原文证据]
  - ...

- **不足与改进：**

| 不足 | 证据 | 改进方向 |
|------|------|----------|
| [问题描述] | [章节/行号] | [具体建议] |

---

## 5. 可复用方法论
[填入步骤 3 提取的方法论清单]

---

## 6. 建议的下一步行动

按优先级排序的改进路径：

1. [最重要的改进 + 建议使用的模式]
2. [次要改进 + 建议使用的模式]
3. ...

**路径参考**：
- 存在能力缺失或架构问题 → `--rewrite` 重构技能
- 仅表达精简问题 → `--simplify` 快速精简
- description 触发不准 → `--optimize-desc` 优化触发
- 需验证实际效果 → `--eval` 建立基准测试
- 整体成熟度高，无明显问题 → 技能状态良好，可直接使用

---

## 附录：基线快照
[插入步骤 1 提取的完整功能基线]
```

## 分析质量要求

1. **证据驱动**：每个判定必须引用原文作为论据，标注具体位置（章节名 / 行号）
2. **优缺并重**：不偏废——既要发现值得学习的设计亮点，也要指出阻碍效果的真实不足
3. **可操作性**：每个不足必须紧跟具体可执行的改进方向，关联到现有模式（--rewrite / --simplify / --optimize-desc / --eval）
4. **深度优先**：追求洞察深度而非覆盖广度，抓住本质问题
5. **方法论沉淀**：从每个分析中提炼可推广的设计模式
6. **用户价值闭环**：评估技能输出是否直接服务于用户终端目标，路径是否最短
7. **只读承诺**：分析过程**绝不修改任何文件**，纯诊断输出

## 输出规范

分析完成后，输出完整的结构化报告（遵循步骤 4 的报告格式）。

报告用中文输出，所有技术术语保持英文（如 SKILL.md、references/、--rewrite 等）。

**禁止**：
- 未经用户同意直接进入重写/优化流程
- 给出没有原文证据支撑的判断
- 使用「总体来说不错」之类的空话
- 建议用户「根据实际情况决定」（必须给出明确的优先级和下一步建议）
- 只找问题不看优点（优秀设计同样值得识别和学习）

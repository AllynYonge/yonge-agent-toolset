# 配置设计 - 带持久化配置技能的编写方法论

## 核心定位

配置类文档的主要失败模式不是报错，而是静默失效。用户按文档写下了完全合法的配置，技能却当它不存在——没有任何提示，表现为「我明明配了却没生效」。这类问题的排查成本远高于配置本身的复杂度，因为用户没有任何线索可循。因此配置的分层、优先级与格式约束必须在动笔前定好，而不是等技能长出第五个后端时再补。

> 本文件是 SKILL.md `### 配置设计（条件适用）` 小节的展开，不是一条独立工作流。是否适用、何时加载，以该小节为准。
>
> 本文件只讲设计原则。目录、文件格式、优先级链、密钥位置和读取脚本已经统一规定，见 [config-paradigm.md](config-paradigm.md)，不要按本文件另行设计。

## 何时适用

目标技能存在以下任一情形时适用：

- 需要持久化用户偏好（默认值、开关、路径）
- 需要凭据或密钥入口
- 需要在多个后端 / 平台 / 供应方之间选择

三者皆无则整块跳过，不必为「将来也许会有配置」预留结构。

---

## 一、按被读时机切三层承载位置

配置内容天然分三种使用时机，对应三个承载位置：

1. **主文件** — 只写查找路径链、键名清单、优先级、以及指向另两层的指引。这四样每次执行都要判断，必须常驻上下文，因此要压到十几行。
2. **schema 文档** — 字段的类型、取值域、默认值。只在真正要读写配置文件时才需要，属于按需加载。
3. **首次设置文档** — 问用户什么、选项怎么排、答案怎么落盘。只在首次设置那一次被读，之后永不加载。

**判据**：一段配置内容若在 90% 的执行里都用不到，它就不该在 SKILL.md 里。反过来，优先级链这种每次都要判断的东西，再短也必须留在主文件。

## 二、配置缺失做成硬门禁

不设门禁时，模型遇到「没有配置文件」会自行挑一个默认值继续跑——用户永远不知道自己在用什么设置，也不知道有配置这回事。把它写成阻塞步骤，缺配置就从静默兜底变成必须先问清楚：

```markdown
## Step 0: 加载配置 ⛔ BLOCKING

本步骤 MUST 在任何实际操作之前完成。
```

配套两分支判定，避免「改一个字段要重答一整套问题」：

- **已有配置** → 加载、解析、应用
- **已有但关键字段为空** → 只问那一个字段，不重跑整套设置

## 三、优先级链单行声明，且与实现逐字对齐

配置来源一多，最常见的错就是搞错谁覆盖谁。写成一行链条，比分散在各处描述有效得多：

```
CLI 参数 > 配置文件 > 环境变量 > 项目 .env > 用户 .env
```

反直觉的那一条要显式举例，否则读者会按自己的直觉理解。例如「配置文件覆盖环境变量」与多数人的预期相反，就该补一句：若配置文件写了 `default_model: A`、环境变量写了 `B`，最终取 A。

**代价**：文档承诺的每一个查找位置，实现必须真的去查。文档多列一个路径而实现不查，用户把配置放到那里就会被静默忽略；若配置又是硬门禁，症状会变成「我配了它却还问我一遍」。

## 四、可变项建模成映射，不要预先组合

同一组字段在每个后端上都要有一份时，有两种写法：

```yaml
# 映射式 —— 新增一个后端只加一行
default_model:
  alpha: null
  beta: null

# 组合式 —— 新增一个后端要加 N 行，且分散在多处
alpha_model: null
alpha_concurrency: null
beta_model: null
beta_concurrency: null
```

前者对。后者把「后端」和「字段」两个可独立变化的维度预先乘在了一起，条目数随维度取值相乘增长。

**判据**：新增一个后端时，只需改一处即为达标；若要在多个位置各加一行，说明维度被预先组合了。

## 五、清单单一事实来源

配置文档最容易腐化的地方是「可选值清单」——后端名单、模型名单、枚举取值域。一份清单在几处各写一遍，就有几个漂移源：改一处漏一处，文档之间开始自相矛盾，而读者无法判断哪份是对的。

只在一个地方写定，其它位置写「见 X」。这条对结构图、schema、字段表同样适用。

## 六、示例不含默认值

把所有默认值都写全的「完整示例」，用户会照抄；抄完即固化。将来实现调优了默认值，对这位用户无效，而他并不知道自己覆盖了什么。

正确分工：

- 默认值只出现在字段表的 Default 列
- 示例只展示「用户真的需要覆盖」的那几项
- 另给一个最小示例，示范「最少写多少就能跑」

## 七、声明手写配置的实际格式约束

只要解析器不是标准库实现（为免依赖而手写的简易解析器很常见），文档就必须交代实现容忍的写法边界：

- 缩进要求（是否只支持固定层级缩进）
- 能否使用行内注释
- 能否使用 flow / inline 风格的映射与数组
- 未知键如何处理（报错还是静默丢弃）
- 非法值如何处理（报错还是原样透传）

不写的后果：用户写出一段完全合法的配置，解析器静默丢掉，且没有任何报错。这类静默失败比直接报错糟得多——报错至少指明了位置。

## 八、多入口标注等价关系

同一个配置项常有多个入口：CLI 参数、配置文件字段、环境变量。文档要让读者一眼看到三者的对应关系，例如在字段表里加一列「等价 env」。

不标注的后果是用户误以为它们是三套独立机制，于是三处都配一遍，再被优先级链的实际行为绕晕。

## 验证动作

解析器为手写实现时，光读文档只能发现一半问题，另一半必须实测。取若干刁钻片段直接喂给解析器，观察实际行为：

- 合法但非常规的 flow / inline 写法
- 未知键
- 非法枚举值
- 带行内注释的值
- 非常规缩进层级
- 版本号高于实现支持的版本

静默丢弃与静默透传这两类行为，文档和代码注释里通常都不会写，只有实测能确认。测出来的真实边界，回写到技巧七的格式约束说明里。

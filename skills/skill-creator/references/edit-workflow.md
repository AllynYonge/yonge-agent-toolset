# 定点编辑模式 - 局部修改工作流

## 核心定位

对技能文档进行**用户驱动的局部修改**——加、改、删、移动具体内容。不做全局诊断，不进评测循环，改完即走。

编辑的驱动力是用户的明确指令，而非系统诊断结果。区别于其他模式：

| 允许 | 禁止 |
|------|------|
| 修改用户指定的段落/规则/示例 | 顺手重构未被提及的章节 |
| 新增用户要求的内容 | 自行判断"应该还要改 X"并执行 |
| 删除用户要求删除的内容 | 删除用户未提及但你觉得多余的内容 |
| 移动内容到用户指定的位置 | 因"更合理"而移动用户未提及的段落 |
| 处理修改引发的连锁影响 | 将连锁影响扩大为全局重构 |

## 工作流

### 步骤 1：阅读技能全貌

完整阅读目标技能的 SKILL.md + 修改可能涉及的 references/ 文件。

**目的**：建立对技能结构、工作流、约束、术语的完整理解——这是后续追问和影响评估的基础。没有这一步，你无法问出有针对性的澄清问题，也无法判断修改是否引发连锁影响。

**记录**：
- 技能的章节结构和层级关系
- 关键术语的使用方式
- 各章节之间的引用和依赖关系
- references/ 文件被引用的位置和时机

### 步骤 2：理解意图

根据意图精确度分流：

**A. 意图已可无歧义执行** — 直接进入步骤 3

判断标准：你能准确说出「改什么 + 改成什么 + 在哪里改」三要素。

例如：
- "把第 47 行的'子智能体'改成'子 agent'"
- "在步骤 3 后面加一个步骤 4，内容是 XXX"
- "删掉关于 Cowork 适配的那段"

**B. 存在歧义** — 追问澄清

追问规则：
- **利用步骤 1 的知识**：你已经读过技能全貌，追问应基于你对技能的理解，而非泛泛的"你想改哪里"
- **每轮必须推进理解**：不能重复问同一层面的问题
- **终止条件**：当你能无歧义地描述出修改的「改什么 + 改成什么 + 在哪里改」时，停止追问

追问方向（按需选用，不必全问）：
- 你指的是 §X 还是 §Y？（定位歧义）
- 改完之后这段要达到什么效果？（效果歧义）
- 你希望用什么风格/措辞？有参考吗？（表达歧义）
- 这段有 3 处类似表述，全改还是只改其中一处？（范围歧义）

**禁止**：
- 追问与修改无关的技能战略问题（那是 --create 或 --analyze 的事）
- 试图把用户引入"也许你应该重写整段"的方向

### 步骤 3：影响评估

对修改涉及的段落及其上下文进行影响分析：

#### 3.1 连锁引用检查

| 检查项 | 方法 |
|--------|------|
| references/ 同步 | 修改的内容是否在 references/ 中有对应/重复/被引用的段落？ |
| description 触发词 | 修改是否影响技能的触发范围？frontmatter description 是否需要同步？ |
| 交叉引用 | 修改的章节是否被其他章节显式引用（如"见 §X"、"如步骤 2 所述"）？ |
| 术语一致性 | 若修改涉及术语变更，其他位置是否还有旧术语？ |

#### 3.2 新增内容的额外检查（仅当操作类型为"新增"时）

| 检查项 | 判断标准 |
|--------|----------|
| 放置位置 | 新内容放在指定位置是否符合指令放置原则？是否会被"中间迷失"吞没？ |
| 语义重叠 | 技能中是否已有语义相近的内容？若有，应扩展现有内容还是另起一段？ |
| 层级归属 | 新内容应在 SKILL.md 正文还是 references/？（参照渐进式披露原则） |

#### 3.3 处理连锁影响

- 若无连锁影响 → 直接进入步骤 4
- 若有连锁影响 → 告知用户具体影响，确认处理范围：
  - 用户说"一并处理" → 将连锁修改纳入步骤 4 的草案
  - 用户说"只改我说的" → 仅执行主修改，在变更摘要中标注未处理的连锁影响

### 步骤 4：草拟变更 & 预览

**先展示，不直接写入。**

#### 4.1 展示格式

对每处修改，展示前后对比：

```markdown
### 修改 1：[简述]

**修改前**（§X / L行号）：
> [原文]

**修改后**：
> [新文]

**理由**：[为什么这样改——如果修改逻辑不自明的话]
```

多处修改时逐项展示，用户可对每项独立回应。

#### 4.2 用户确认协议

| 用户回应 | 处理 |
|----------|------|
| 接受（"好"/"可以"/"就这样"） | 进入步骤 5 执行 |
| 部分接受（"第 1 个好，第 2 个不太对"） | 接受的部分进入步骤 5，被否的部分修改草案后重新展示 |
| 要求调整（"方向对但措辞改一下"） | 修改草案后重新展示该项 |
| 否决（"不对""不是我要的"） | 记录否决次数 |

#### 4.3 不满意回路

- 某项修改首次被否 → 修改草案，重新展示
- 同一处修改**连续两次被否** → 退回步骤 2，重新澄清意图（此时大概率是一开始就理解错了修改方向，继续微调草案不会收敛）

退回时说明原因："这处修改两次没对上你的预期，我可能理解偏了。能再描述一下你期望的效果吗？"

### 步骤 5：执行 & 八原则自检

#### 5.1 写入变更

按用户确认的内容写入文件。

#### 5.2 八原则质量门禁

对修改涉及的段落（不是全文）做八原则全量检查：

| # | 原则 | 检查焦点 |
|---|------|----------|
| 1 | 渐进式披露 | 新增内容是否让 SKILL.md 超长？是否应在 references/？ |
| 2 | 扩展性 | 修改是否引入了硬编码的同构条目？ |
| 3 | 结构组织规范 | 修改后的段落在上下文中是否顺序合理、同类相邻？ |
| 4 | 指令放置 | 若修改了关键规则，新位置是否在认知优势区？ |
| 5 | 交互式引导 | 修改是否影响了用户的操作路径清晰度？ |
| 6 | 重点解释性 | 修改/新增的指令是否有 WHY？还是只有 MUST？ |
| 7 | 术语一致性 | 修改引入的术语是否与全文一致？ |
| 8 | 表达精简 | 修改是否引入了冗余表述？ |

**自检性质**：这是质量护栏，不是诊断报告。

- 通过 → 不需要额外说明
- 发现降级 → 标注在变更摘要中，但**不阻断执行**（用户的修改指令优先）

#### 5.3 用户指令与原则冲突的处理

| 冲突程度 | 处理方式 |
|----------|----------|
| 轻度降级（如：新增段落稍显冗长，但语义无损） | 执行后在摘要中标注 |
| 明显违反核心原则（如：用户要求删除所有 WHY 解释） | 执行前告知后果，用户确认后执行 |

告知格式：
> 这样改会导致 [具体后果]，因为违反了 [原则名]。你确定要这样改吗？

用户确认 → 执行并在摘要中记录为"用户知情选择"。

### 步骤 6：变更摘要

```markdown
## 变更摘要

**改了什么**：
- [修改 1 简述]
- [修改 2 简述]

**没碰什么**：
- [明确列出用户可能以为被改了但实际没动的部分]

**自检结果**：
- 八原则检查：[全部通过 / 原则 X 有轻度降级：具体描述]

**连锁影响**：
- [已处理 / 未处理但建议后续关注的点]

**[顺带发现]**（可选）：
- [执行过程中观察到的、与本次修改无关的其他问题。只列出，不执行。]
```

"顺带发现"区块的约束：
- 仅当确实观察到值得提及的问题时才出现
- 不超过 3 条
- 每条一句话，点到为止
- 绝不自动执行

---

## 硬约束（汇总）

1. **不延伸**：只改用户明确要求的内容。观察到的问题放入"顺带发现"，不主动修复。
2. **不诊断**：不做全局质量分析（那是 --analyze 的事）。
3. **不循环**：不进入评测-反馈-改进循环（那是 --improve 的事）。
4. **不阻断**：自检发现降级不构成拒绝执行的理由。用户指令优先。
5. **先读后问**：必须先完整阅读技能，再追问或执行。
6. **先展示后写入**：任何修改在写入文件前必须获得用户确认。

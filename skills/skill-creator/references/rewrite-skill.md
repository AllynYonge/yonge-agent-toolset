# 重写模式 - 技能文档重写方法论

## 核心定位

在**不改变技能行为**的前提下，通过结构重组、内容分层、歧义消除和规范化处理，提升技能文档的清晰度、可维护性和指令遵从率。

重写的对象是文档本身（SKILL.md + references），而非技能的功能逻辑。重写前后，技能在相同输入下应产出相同输出。

| 允许 | 禁止 |
|------|------|
| 调整段落顺序和层级结构 | 增删功能或改变技能意图 |
| 将过长正文拆分到 references/ | 引入原文不存在的新策略或框架 |
| 合并重复/冗余指令 | 改变工作流步骤的逻辑顺序 |
| 将模糊表述替换为精确表述 | 删除有效的约束条件 |
| 统一术语和概念命名 | 添加原文未暗示的新约束 |
| 移动关键规则到首尾位置（认知位置优化） | 改变输出格式的核心要求 |
| 补充缺失的章节分隔和导航标记 | 改变角色设定或技能身份 |
| 将写死的同构条目抽象为可插拔数据 | 改变触发条件或适用范围 |
| 添加引用链接和阅读时机说明 | 重新设计技能的方法论（道/法层） |

## 诊断维度

以下七个维度直接源自本技能（skill-creator）自身的编写原则。每个维度有明确的检查项和判定标准。

### D1: 渐进式披露

检查技能是否正确执行三级加载策略。

**检查项：**
- SKILL.md 是否超过 500 行？
- 仅特定模式才需要的详细内容是否错误地留在正文中？
- 参考文件是否有清晰的引用链接和阅读时机说明（"何时阅读"）？
- 大型参考文件（>300 行）是否有目录？
- 三级加载（元数据 / 正文 / 资源）是否合理划分？

**判定**：正文超 500 行、或存在仅特定模式使用却未抽离的大块内容（>50 行），即为违规。

### D2: 指令放置效能

检查关键指令是否利用了认知位置效应。

**检查项：**
- 核心身份和最硬约束是否在 SKILL.md 最顶部（首因效应）？
- 最关键的 2-3 条行为规则是否在文件末尾用不同措辞重申（近因效应）？
- 关键规则是否被埋在文件中间三分之一（中间迷失）？
- 存在可能冲突的规则时，是否有显式优先级声明？

**判定**：关键约束仅出现在中段、或冲突规则无优先级声明，即为违规。

### D3: 可扩展性

检查技能结构是否支持低成本演进。

**检查项：**
- 能力模块是否解耦（可独立新增或移除，无需改动其他部分）？
- 是否存在**不对称**——平级事物用了不同机制（一个靠新文件，另一个靠改正文）？
- 是否存在**被拍平的组合**——独立维度被写死为一维清单？
- 会增长的东西（模式、平台、变体）是否用统一的可插拔方式表达？
- 新增一种模式或变体是否需要改动不止一个既有段落？

**判定**：存在不对称或被拍平组合坏味道，即为违规。

### D4: 文档基本规范

检查文档的可读性和可执行性。

**检查项：**
- 整体结构与操作步骤是否逻辑清楚、层次分明？
- 语言是否简单直接（无晦涩新概念或自造黑话）？
- 是否高度可执行（有直观步骤与示例）？
- 是否有交互式上手引导（主动检测缺失输入、索要关键信息、引导决策点）？

**判定**：流程跳跃、缺乏示例、或假设用户已读完全文才能操作，即为违规。

### D5: 写作风格

检查指令的表达方式是否高效。

**检查项：**
- 关键规则是否解释了 WHY（而非只写 MUST）？
- 是否存在过度使用全大写 ALWAYS/NEVER 而不附带理由的情况（黄旗）？
- 指令是否用祈使句？
- 是否存在不出力的内容（读了但不影响执行的段落）？
- 是否过度堆砌刚性约束而非引导理解？

**判定**：大量无理由的 MUST/NEVER、或存在可删除而不影响行为的废段，即为违规。

### D6: 结构组织

检查文件和目录的组织方式。

**检查项：**
- 目录结构是否规范（SKILL.md / scripts / references / assets）？
- 领域/框架变体是否按独立参考文件组织（而非全写在正文中）？
- 章节之间的逻辑依赖是否顺序正确（先定义再引用）？
- 不同职责的内容是否混杂在同一章节？
- 模块边界是否有清晰的分隔标记？

**判定**：职责混杂、依赖倒置、或变体未独立组织，即为违规。

### D7: 一致性与术语

检查文档内部的统一性。

**检查项：**
- 同一概念是否使用了多种名称（如"子智能体/子agent/subagent"混用）？
- 格式风格（列表、标题级别、标签）是否统一？
- 语气是否一致（祈使句 vs 陈述句 vs 疑问句混用于指令中）？
- 中英文术语选择是否一致（一处用中文一处用英文指代同一事物）？

**判定**：同一概念有 2 种以上称呼、或格式风格不统一，即为违规。

## 工作流

### 步骤1：功能基线提取

读取目标技能的 SKILL.md 及其所有 references/ 文件，提取并记录：

1. **核心意图（道）**：技能为什么存在？解决什么 Claude 原生处理不好的问题？
2. **方法论（法）**：技能采用什么策略、框架或心智模型？
3. **功能清单（术）**：逐项列出所有独立功能和模式（每个用一句话描述）
4. **约束清单**：所有正向和负向约束
5. **工作流逻辑**：各步骤的顺序、依赖关系和条件分支
6. **输出规格**：各模式的输出格式要求

此基线是最终验证的锚定标准——重写结果必须覆盖基线中的每一项。

### 步骤2：文档质量诊断

按 D1-D7 七个维度逐一检查。对每个维度：

1. 给出判定：**有问题** / **无问题**
2. 有问题时：
   - 引用原文具体位置（行号或章节名）作为证据
   - 评估严重度：**高**（严重影响指令遵从率或可维护性）/ **中**（有改进空间但不紧急）/ **低**（细微瑕疵）
   - 描述修复后的预期效果

### 步骤3：交互式维度选择

向用户展示诊断结果，**等待用户选择后方可执行重写**。

**展示格式：**

```markdown
根据对照技能编写原则的分析，当前技能文档存在以下可重写维度：

| # | 维度 | 严重度 | 发现的问题 | 预期效果 |
|---|------|--------|-----------|----------|
| 1 | 渐进式披露 | 高 | SKILL.md 达 620 行，§X 的详细内容仅 --foo 模式使用 | 正文精简至 ~450 行 |
| 2 | 指令放置 | 中 | 核心约束"不得..."位于文件第 312 行（中间迷失区） | 移至顶部，遵从率提升 |
| ... | ... | ... | ... | ... |

请选择要执行的维度（如 `1,3,5` 或 `all`）：
```

**规则：**
- 仅展示实际存在问题的维度（无问题的维度不列出）
- 每条「发现的问题」必须有原文证据（不能凭空断言）
- 用户回复前，不输出 `<rewritten_skill>`

### 步骤4：针对性重写执行

仅对用户选定的维度执行重写。按以下优先级处理（高优先级先做，因为后续维度可能依赖其结果）：

1. **结构组织（D6）** — 基础骨架正确后，其他维度才有稳定的定位
2. **渐进式披露（D1）** — 内容分层决定了哪些内容留在正文
3. **可扩展性（D3）** — 消除坏味道可能涉及文件拆分
4. **指令放置（D2）** — 在最终结构上做认知位置调整
5. **文档基本规范（D4）** — 流程和可执行性优化
6. **写作风格（D5）** — 措辞和解释层面的改进
7. **一致性与术语（D7）** — 最终抛光

每个维度的修改应记录在变更日志中（原文位置 → 新位置/新内容）。

### 步骤5：基线验证

逐项核对步骤1提取的功能基线：

- [ ] 每个功能点在重写后仍存在且可被识别
- [ ] 每个约束条件未被删除或弱化
- [ ] 工作流逻辑和步骤顺序未改变
- [ ] 输出格式要求完整保留
- [ ] 核心意图未发生偏移
- [ ] 参考文件引用路径正确且可到达

若任何一项不满足，回退修正后再输出。

| 1 | ... | 高/中/低 | ... | 原文§X / L行号 | ... |

## 请选择要执行的维度

## 典型重写操作示例

### 示例1：渐进式披露修复

**问题**：SKILL.md 正文 580 行，其中「评测步骤详解」120 行仅 --eval 模式使用。

**重写前**（正文内）：
```markdown
## 评测步骤

### 步骤 1：拉起运行
[... 120 行详细步骤 ...]
```

**重写后**（正文）：
```markdown
## 评测步骤

本节是连续序列——不要中途停下。结果放在 `<skill-name>-workspace/`。

详细五步流程见 [eval-workflow.md](references/eval-workflow.md)。运行评测时阅读。
```

### 示例2：可扩展性重构

**问题**：三种输出模式（JSON、Markdown、HTML）各写一段 30 行的处理逻辑，新增格式需改正文。

**重写前**：
```markdown
### JSON 输出
[30 行处理逻辑]

### Markdown 输出
[30 行处理逻辑]

### HTML 输出
[30 行处理逻辑]
```

**重写后**：
```markdown
### 输出格式处理

每种格式一个参考文件，按统一结构组织：

| 格式 | 参考文件 | 何时使用 |
|------|---------|---------|
| JSON | [json-output.md](references/json-output.md) | 用户要求机器可读输出时 |
| Markdown | [md-output.md](references/md-output.md) | 默认人类可读输出 |
| HTML | [html-output.md](references/html-output.md) | 用户要求富文本或可视化时 |

新增格式：创建同构参考文件并加入上表即可。
```

### 示例3：指令放置优化

**问题**：技能最重要的约束（"所有输出必须为中文"）仅出现在文件第 287 行。

**重写前**：只在中段某处提及一次。

**重写后**：
- 文件顶部（紧接 frontmatter）：`<critical-rules>` 中明确列出
- 文件末尾：用不同措辞重申（"再次强调：本技能的全部输出使用中文，无例外"）
- 原位置：保留但标注为"详见顶部 critical-rules"

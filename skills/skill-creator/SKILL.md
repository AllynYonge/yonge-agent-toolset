# 技能创建器

用于创建新技能并迭代改进它们的技能。

从高层次看，创建技能的流程大致如下：

- 确定你希望技能做什么，以及大致如何做
- 编写技能草稿
- 准备几个测试提示词，并在「能访问该技能的 Claude」上运行
- 帮助用户从定性与定量两个角度评估结果
  - 运行在后台时，若还没有定量评测，先起草一批（若已有，可原样使用，或在你认为需要时修改）。然后向用户解释这些评测（若本来就有，就解释现有那套）
  - 用 `eval-viewer/generate_review.py` 脚本把结果展示给用户查看，并让他们一并看定量指标
- 根据用户对结果的评估反馈重写技能（若定量基准测试暴露出明显缺陷，也要一并处理）
- 重复，直到满意
- 扩大测试集，在更大规模上再试

使用本技能时，你的工作是判断用户处在流程的哪个阶段，然后介入并帮助他们推进。例如对方说「我想为 X 做一个技能」——你可以帮他们收窄意图、写草稿、写测试用例、弄清如何评测、跑完所有提示词，再循环。

反过来，若他们已有技能草稿，你可以直接进入循环中的评测 / 迭代环节。

当然，始终要灵活：若用户说「我不需要跑一堆评测，就凭感觉一起推进」，那就按他们说的来。

技能完成之后（顺序同样可以灵活），你还可以再跑技能描述改进器——我们另有一整套独立脚本——用于优化技能的触发。

## 快捷入口模式

用户可用标志直接跳到特定阶段：

- `--create` — 从零创建新技能（意图捕获 → 访谈研究 → 编写 SKILL.md）
- `--edit` — 定点编辑技能内容（加/改/删/移），不需全局诊断或评测循环
- `--analyze` — 只读分析技能质量，生成诊断报告与改进建议
- `--rewrite` — 重写重构技能文档（不改行为，只改结构、清晰度、可维护性）
- `--simplify` — 精简冗余内容（rewrite 的"表达精简"子集）
- `--optimize-desc` — 优化 frontmatter description 以提升触发准确率
- `--eval` — 运行评测（跳过用例准备，直接执行测试并评分）
- `--improve` — 根据评测反馈迭代改进技能行为与输出质量
- `--compare` — 盲测对比两个技能版本，判断哪个更优


有标志时，跳过开场铺垫，直接进入对应章节。若缺少必要信息（路径、技能名等），仍要追问，但不要再从头走完整条工作流。

没有标志时，仍像现在这样从上下文推断入口。

## 创建技能（--create）

### 技能设计框架

在写任何指令之前，先把技能拆到三层：

**道（战略意图）** — 这个技能为什么存在？

- 它解决了什么 Claude 在没有它时处理不好的核心问题？
- 独特价值是什么——若没有这个技能，会失去什么？
- 这是「控制型」技能（强制一致性），还是「探索型」技能（启发创造力）？

**法（方法论）** — 它将采用什么方法？

- 技能教给 Claude 哪些策略、心智模型或框架？
- 处理模糊情况时的决策逻辑是什么？
- 它与 Claude 的默认行为有何不同？

**术（执行）** — 哪些具体指令落实该方法论？

- 每条指令都应能回溯到某个「法」（若不能，质疑它是否属于这里）
- 优先解释推理，而不是发号施令
- 将服务于同一方法论目标的相关指令归组

把这当作诊断工具：若技能大半是「术」（一串「做这个、做那个」）却没有清晰的「道」和「法」，它会脆弱且难维护。若「道」清楚却没有「术」，结果就不会稳定一致。

### 捕获意图

先理解用户意图。当前对话可能已包含用户想固化的工作流（例如他们说「把这个变成技能」）。若是，先从对话历史提取答案——用过的工具、步骤顺序、用户做过的纠正、观察到的输入/输出格式。用户可能需要补齐空白，并应在进入下一步前确认。

**道 — 战略问题：**

1. 这个技能解决什么问题？（不是「它做什么」——而是为什么必须存在？）
2. 何时应触发本技能，何时应由 Claude 原生处理？

**法 — 方法问题：**
3. 技能应遵循什么方法论或框架？
4. 边界情况与模糊性应如何处理？

**术 — 实现问题：**
5. 预期输出格式是什么？
6. 是否应建立测试用例？（按技能类型建议：客观可验证的输出受益于测试用例；主观输出通常不需要）
7. 技能是否需要持久化配置（用户偏好、凭据、多后端选择）？若需要，配置项有哪些入口，谁覆盖谁？（优先级链是事后补加成本最高的决策，此刻确认可避免返工）

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准与依赖。在这部分理顺之前，先不要写测试提示词。

检查可用的 MCP——若对研究有帮助（查文档、找类似技能、查最佳实践），有子智能体则并行研究，否则内联进行。带着上下文来，减轻用户负担。

### 编写 SKILL.md

根据用户访谈，填好这些部分：

- **name**：技能标识符
- **description**：何时触发、做什么。这是主要触发机制——既要写技能做什么，也要写何时使用的具体情境。所有「何时使用」信息放在这里，不要放正文。注意：目前 Claude 有「欠触发」技能的倾向——在技能本该有用时却不用。为对抗这一点，请把技能描述写得稍微更主动、覆盖面更广一些。例如，与其写「How to build a simple fast dashboard to display internal Anthropic data.」，不如写「How to build a simple fast dashboard to display internal Anthropic data. Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a 'dashboard.'」
- **compatibility**：所需工具、依赖（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

技能应符合以下结构和原则。这既是编写指南，也是重写模式（--rewrite）的诊断标准。

#### 渐进式披露原则

本原则回答"内容按什么时机、什么层级加载"——不该一次性全塞进上下文。

技能采用三级加载：

1. **元数据**（name + description）— 始终在上下文中（约 100 词）
2. **SKILL.md 正文** — 技能触发时进入上下文
3. **捆绑资源** — 按需加载（无上限；脚本可不加载正文即可执行）

捆绑资源按用途分三类，这也是技能的标准目录结构（全文以此为准，其它章节引用此处而不重画）：

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

**核心原则：每次必读的内容留在 SKILL.md 主文件。**

抽离到 references/ 有真实成本：
- 每次读取额外消耗 token
- 增加文件 I/O 降低效率
- 只有两种情况才应抽离：
  1. **按需加载** — 只在特定条件/模式下才需要的内容（如多领域技能中每次只用一个领域的详细指令）
  2. **内容极大** — 单个主题的详细内容超过 300 行，且无法精简

**何时保留在 SKILL.md：**
- 核心工作流、通用规则、关键约束 — 无论多长都保留
- 每次执行都需要的参考信息 — 即使 100-200 行也保留
- 所有模式共享的方法论 — 不要因为"看起来多"就拆出去

**何时抽离到 references/：**
- 多领域/多框架技能，每次只用其中一个变体的详细指令
- 单个主题的详细展开超过 300 行且无法压缩（如完整的 schema 定义、大型示例集）
- 纯参考性质的补充材料，多数执行路径用不到

**领域组织示例**：当技能支持多个领域/框架时，把每个变体拆成独立参考文件（每次只加载一个），SKILL.md 保留工作流与选择逻辑：

```
cloud-deploy/
├── SKILL.md (workflow + selection logic)
└── references/
    ├── aws.md      (only loaded when user chooses AWS)
    ├── gcp.md      (only loaded when user chooses GCP)
    └── azure.md    (only loaded when user chooses Azure)
```

**反例（过度拆分）：** 不要把"每次都要用的 50 行规则"拆成 references/rules.md — 虽然减少了 SKILL.md 长度，但每次执行都要额外读一次文件，净成本更高。

#### 扩展性原则

本原则回答"一项技能该拆成哪些能力、怎么拆"的问题，与渐进式披露原则（加载时机）、结构组织规范原则（内容排布）正交。一项技能的各个能力应当彼此独立——每一块都可以单独演进、新增或移除，无需回头重写其他部分。各能力之间通过清晰的边界（参考文件、约定一致的结构、明确的路由指引）衔接，这样技能不断扩充时，复杂度不会随之等比上升。

**找出会增长的东西，用统一方式表达。** 在多数技能中，总有一类元素会反复出现并持续增加——写作技能中的平台与风格、API 封装中的 endpoint、流水线中的阶段等。应尽早识别这一类元素，为其设计统一、可插拔的表达方式（如为每条创建一个数据文件，或采用同构结构），而不是将每个实例写死在正文中。

**达标判据：** 添加下一个实例时，如果只需新增一个数据文件而无需修改任何指令，即为扩展性达标；如果需要回头修改正文，说明这类元素尚未被建模为数据。

这类征兆本质只有一条：**新增或演进一个实例时，被迫回头改动它自身数据文件以外的地方。** 只要出现这种被迫，就说明这类元素没被干净地建模成数据。它有多种表现，常见的有：

- **散落硬编码** — 变体没有各自成文件，而是以并列段落、条件分支说明或清单项直接写死在 SKILL.md 正文里，加一个变体就要在正文里插一段。根因是它从未被建模为数据。
- **同类实例的扩展机制不一致** —  同一类事物中，有的只需新增实例文件，有的却还要修改正文或路由逻辑。只要实例属于同一扩展点，就应采用同一种定义、发现和加载机制。
- **实例定义混入通用流程** —  实例文件除了描述“这个实例是什么”，还重复描述“如何处理这类实例”。通用流程因此散落在多个文件中，流程一变就要同步修改所有实例。实例文件应只保存差异，公共处理流程只保留一份。
- **独立维度被预先组合** — 将多个可以独立变化的维度预先枚举成 `wechat-article`、`wechat-note`、`xhs-note` 等组合实例，会使实例数量随维度取值相乘增长。应分别建模各个维度，在运行时按需组合；新增任一维度的取值时，不应修改另一个维度。（实例文件的拆分方式见渐进式披露原则。）

#### 结构组织规范原则

本原则回答"内容按什么顺序、什么边界排布"才读得通顺——只管文档内部的逻辑排布，目录怎么建见渐进式披露原则，能力怎么切分见扩展性原则。

- **顺序**：章节之间的逻辑依赖应顺序正确（先定义再引用）
- **同类相邻**：同类或强相关的章节应挨在一起，不被无关内容隔开（如"重写"与作为其子集的"精简"两节应连排，而非中间插入别的模式）
- **低耦合**：不同职责的内容不应混杂在同一章节
- **高内聚**：服务于同一目的的指令应归到一起，不散落在多个章节
- **单一事实来源**：任何结构图、schema、清单只在一处写定，其它地方交叉引用，不复制——复制会制造漂移源，改一处漏一处就自相矛盾

#### 指令放置原则

技能就是提示词——认知位置效应同样适用：

- **首因效应（Primacy）**：模型最先读到的内容锚定其行为。把技能的核心身份与最硬约束放在 SKILL.md 正文最顶部，紧接 frontmatter。
- **近因效应（Recency）**：上下文结束前最后读到的内容权重偏高。在文件末尾用不同措辞重申 2–3 条最关键行为规则（不要原文粘贴）。
- **中间迷失（Lost in the Middle）**：长文件会稀释中段指令。若 SKILL.md 接近 500 行，把详细参考材料移出——不要让关键规则埋在中间三分之一。
- **层级清晰**：当规则可能冲突时，显式声明优先级（例如「若 X 与 Y 冲突，以 X 为准」）。

解释*为什么*某条规则重要仍是首选，但即便解释得再好，放错位置也会被忽略。

#### 交互式引导原则

**本质：技能是给"没读过文档的人"用的。** 用户不会先通读 SKILL.md 再开始——他们边用边问。所以技能既要写得让人扫一眼就能上手，运行时又要主动把人带过一遍，而不是假设对方已经读完。下面两层都服务于这个本质。

**文档怎么写**（让人不必读完就能抓住用法）：
- **流程清晰**：整体结构与操作步骤逻辑清楚、层次分明
- **语言朴素**：用简单直接的语言，不发明晦涩新概念或黑话
- **可执行**：通过直观步骤与示例，让用户不必读完全部细节也能抓住核心用法

**运行时怎么带用户**（不假设对方读过工作流）：
- 检测缺什么，主动索要关键输入
- 只在真正需要决策的点上抛出问题
- 按顺序走完步骤，而不是甩给用户一堆选项

#### 重点解释性原则

**阐明规则背后的理由**

LLM 具备很强的理解和推理能力。当你为它提供一条规则或指令时，如果同时说明背后的原因，它就能在遇到你未曾预见的情况时举一反三，做出符合原意的正确判断。相反，如果只给出一条缺乏上下文的指令，LLM 往往会机械地执行，一旦实际场景偏离你制定规则时的预设，指令就会失效。**建议：** 针对具有一定开放性的指令或规则，考虑附上其设计意图或背后的理由。

**优先使用正向表述**

在编写指令时，应优先明确说明"该做什么"，而非"不要做什么"。负向表述容易造成理解偏差，且无法有效指引行为方向。**负向表述仅在以下两种场景中使用：**
- 封堵已经观察到的高频错误
- 在提示词的首尾位置强调硬性边界

#### 术语一致性原则

文档内部的统一性：

- 同一概念使用统一名称（避免"子智能体/子agent/subagent"混用）
- 格式风格统一（列表、标题级别、标签）
- 语气一致（祈使句 vs 陈述句 vs 疑问句不混用于指令中）
- 中英文术语选择一致（一处用中文一处用英文指代同一事物）

#### 表达精简原则

**MUST** 加载 [simplify.md](references/simplify.md) ，确保技能编写符合其中规定的要求。

#### 其他技巧说明

- **提示词加权**: 善于使用 `MUST`、`MUST NOT`、`ALWAYS`、`ONLY` 等高强度词汇来强化重要指令。但需要注意，如果滥用此类词汇，会导致整篇提示词失去重点。因此，应**仅在对结果影响最大且最为关键的指令上**使用加权词。

### 配置设计（条件适用）

**适用门槛**：目标技能存在以下任一情形时适用，三者皆无则跳过本节。

- 需要持久化用户偏好（默认值、开关、路径）
- 需要凭据或密钥入口
- 需要在多个后端 / 平台 / 供应方之间选择

配置一旦写错，症状往往是「用户配了但没生效」且无任何报错——这类静默失败的排查成本远高于配置本身的复杂度，所以配置的分层与优先级要在动笔前定好，而不是事后补。

**MUST** 加载 [config-design.md](references/config-design.md)，按其八条技巧落地：三层承载位置、缺失即阻塞、优先级链单行声明、可变项建模成映射、清单单一事实来源、示例不含默认值、声明手写格式约束、多入口标注等价关系。

### 编写模式与示例

指令优先用祈使句。

**定义输出格式** — 输出格式需要严格一致时，硬约束是恰当的，可以这样写：

```markdown
## Report structure
ALWAYS use this exact template（报告结构必须一致，下游解析依赖它）:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式** — 包含示例很有用。可按如下格式（但若示例里已有 "Input" 和 "Output"，可略作变通）：

```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

## 评估测试技能（--eval）

本节从"准备用例"到"运行评测"是一条连续动作——不要中途停下。不要使用 `/skill-test` 或任何其他测试技能。（`--eval` 快捷入口假定"准备测试用例"已完成，可直接从运行开始。）

### 准备测试用例

写完技能草稿后，准备 2–3 个贴近真实的测试提示词——真实用户会真的说出口的那种。与用户分享：[不必原样使用这句]"这是我想试的几个测试用例。看起来对吗，还是要再加？"然后运行它们。

把测试用例保存到 `evals/evals.json`。先不要写断言——只写提示词。下一步会在运行进行期间起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

上面是最小示例，只为快速展示形状；字段全集（含稍后才加的 `assertions`）以 `references/schemas.md` 为准。

### 运行评测

结果放在与技能目录同级的 `<skill-name>-workspace/`。工作区内按迭代组织（`iteration-1/`、`iteration-2/` 等），每个测试用例再有自己的目录（`eval-0/`、`eval-1/` 等）。不要事先建齐——边做边建。

详细的五步流程（拉起运行、起草断言、捕获计时、评分聚合、读取反馈）见 [eval-workflow.md](references/eval-workflow.md)。运行评测时阅读。

## 改进增强技能（--improve）

这是循环的核心。测试用例已跑完，用户已审过结果，现在要根据反馈把技能做更好。

### 如何思考改进

1. **从反馈中概括。** 这里的大图景是：我们在做的技能将来可能被用一百万次（也许字面如此，甚至更多谁知道），覆盖许多不同提示词。你和用户只在少数几个例子上反复迭代，因为这样推进更快。用户对这些例子了如指掌，评估新输出也快。但若共同打磨的技能只对这些例子有效，就没用了。与其塞进抠细节的过拟合改动，或令人窒息的 MUST，若有顽固问题，不妨换隐喻、换工作模式试试。尝试成本相对低，也许能撞上更好的东西。

2. **保持提示词精简。** 删掉不出力的内容。务必读转录，而不只看最终输出——若技能让模型在无产出的事情上浪费大量时间，可以试着去掉导致它那样做的部分，观察结果。

3. **解释为什么。** 尽力解释你要求模型做的每件事背后的**原因**。今天的 LLM *很聪明*。它们有不错的心智理论；给好的 harness，它们能超越死记硬背的指令，真正把事做成。即使用户反馈简短或带火气，也要真正理解任务、理解用户为何那样写、实际写了什么，再把这种理解写进指令。若你发现自己在写全大写的 ALWAYS/NEVER，或用超级刚性的结构 —— 尽量改框并解释推理，让模型明白你要的东西为何重要。这更人性化、更有力、也更有效。

4. **寻找测试用例间的重复劳动。** 读测试运行的转录，留意子智能体是否各自写出了类似辅助脚本，或对某事采取了相同的多步路径。若 3 个测试用例都让子智能体写出 `create_docx.py` 或 `build_chart.py`，强烈信号：技能应捆绑该脚本。写一次，放进 `scripts/`，并让技能使用它。这样未来每次调用都不必重新发明轮子。

这项任务很重要，思考时间不是瓶颈；慢慢想、好好琢磨。先写修订草稿，再用新眼光审视并改进。尽量代入用户视角，弄清他们想要与需要什么。

### 迭代循环

改进增强技能之后：

1. 把改进应用到技能
2. 把全部测试用例重跑进新的 `iteration-<N+1>/` 目录，包括基线运行。若在创建新技能，基线始终是 `without_skill`（不使用技能）——跨迭代不变。若在改进已有技能，自行判断基线用什么更合适：用户进来时的原版，还是上一轮迭代。
3. 用 `--previous-workspace` 指向上一轮迭代启动审阅器
4. 等用户审完并告诉你做完了
5. 读新反馈，再改进，重复

持续直到：

- 用户说满意了
- 反馈全是空的（一切看起来都好）
- 你已无法取得有意义的进展

## 重写重构技能（--rewrite）

“重写重构技能”与“改进增强技能”是两件不同的事，区别参考如下：

| 模式 | 改变什么 | 不碰什么 | 驱动力 |
|------|----------|----------|--------|
| **--improve** | 技能的行为、输出质量、策略选择 | 用户明确要保留的业务逻辑 | 评测结果 + 用户对输出的反馈 |
| **--rewrite** | 文档的结构、清晰度、一致性、可维护性 | 核心意图、功能集、约束、工作流逻辑 | 文档质量分析（对照本技能的编写原则） |

参考 [rewrite-workflow.md](references/rewrite-workflow.md) 进行重构流程

---

## 精简模式（--simplify）

专门处理技能内容的冗余与臃肿问题。当用户说"这个技能太长了""帮我精简一下""去掉废话"时，使用精简模式。

**本质：精简是 `--rewrite` 只选"表达精简"维度的子集**，复用 rewrite 的「诊断 → 选择 → 执行 → 验证」骨架（见 [rewrite-workflow.md](references/rewrite-workflow.md)），仅在两点不同：

1. **只跑表达精简**：诊断范围锁定表达精简原则，不涉及其余七个原则
2. **换用四档策略**：把 rewrite 步骤 3 的维度勾选，替换为 simplify.md 的细粒度风险分级（保守 / 平衡 / 激进 / 自定义）

---

## 定点编辑（--edit）

用户有明确的局部修改意图（加/改/删/移），不需要全局诊断或评测循环时使用。

### 与其他模式的边界

| 模式 | 驱动力 | 范围 | 需要评测？ |
|------|--------|------|-----------|
| --improve | 评测反馈 | 行为/质量 | 是 |
| --rewrite | 文档质量诊断 | 全局结构 | 否 |
| --simplify | 冗余诊断 | 全文精简 | 否 |
| **--edit** | 用户的明确指令 | 局部定点 | 否 |

### 工作流概要

1. **阅读技能全貌** — 先读后问，建立完整理解
2. **理解意图** — 精确即执行，模糊则追问（动态终止，不限轮数）
3. **影响评估** — 连锁引用、新增内容放置位置、语义重叠检查
4. **草拟变更 & 预览** — 先展示不写入，逐项确认；同一处两次被否则退回意图澄清
5. **执行 & 八原则自检** — 写入后做全量质量门禁，降级标注但不阻断
6. **变更摘要** — 改了什么、自检结果、连锁影响、顺带发现

### 硬约束

- 不做用户未要求的延伸优化（观察到的问题只列入"顺带发现"，不主动修复）
- 不触发全局诊断（那是 --analyze 的事）
- 不进入评测循环（那是 --improve 的事）
- 自检仅作为质量护栏，不作为拒绝执行的理由

详细的六步流程、追问策略、不满意回路、八原则自检方法和变更摘要格式见 [edit-workflow.md](references/edit-workflow.md)。运行 --edit 时阅读。

## 盲测对比（--compare）

若要更严格地比较两个技能版本（例如用户问「新版本是不是真的更好？」），有一套盲测对比系统。细节见 `agents/comparator.md` 与 `agents/analyzer.md`。基本思路：把两份输出交给独立智能体，不告诉它哪个是哪个，让它判断质量；再分析胜者为何胜。

这是可选的，需要子智能体，多数用户用不到。人工审阅循环通常已够用。

## description 优化（--optimize-desc）

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用技能的主要机制。创建或改进增强技能后，主动提出优化 description，以提升触发准确率。

详细的四步流程（生成评测查询、用户审阅、运行优化循环、应用结果）及触发机制说明见 [description-optimization.md](references/description-optimization.md)。运行 --optimize-desc 时阅读。

# 按层改动策略

**核心：改动范围由浅入深，当前层没有进一步收益后再换下一层，不一次跨越多个层级。**

为什么这么定：这样每次进步都能说清是"哪一处改动"带来的（可归因）。如果一轮同时动了描述、
正文和脚本，采纳了也不知道是哪处起作用，丢弃了也不知道该退回哪处。

每轮只允许一个原子改动，且只在当前层。这三层表示改动范围，不表示 skill 文件本身的三级结构。

## 三层改动范围

### 第 1 层：描述 / 触发（description）

- **改什么**：SKILL.md frontmatter 的 `description` 字段
- **目标**：提高该触发时的召回率，并降低不该触发时的误触发率
- **看什么指标**：触发准确率（可调用 creator 的 `run_eval.py` / `run_loop.py`，按 60/40 划分训练样本和测试样本）
- **成本**：低——只运行触发评估（约 20 条查询样本，实际耗时取决于执行后端）
- **进入**：默认起点（触发已经很好可跳过）
- **换层**：连续 K 轮（默认 5）触发准确率没提升

### 第 2 层：正文（body）

- **改什么**：指令措辞、步骤顺序与流程结构、输出模板、规则组织与优先级、解释性文字
- **目标**：提升结果质量（pass_rate）、降低多次运行的行为波动、减少不必要的 token 消耗
- **看什么指标**：行为断言 pass_rate + 质量维度评分
- **成本**：中——每轮运行开发集（Dev）评估
- **进入**：第 1 层换出后
- **换层**：连续 K 轮 pass_rate 没提升

### 第 3 层：脚本 / 引用（script）

- **改什么**：辅助脚本逻辑、引用文件内容与结构、模板文件
- **目标**：提升能力上限，解决正文层无法解决的结构性问题
- **看什么指标**：完整行为测试集 + 性能指标
- **成本**：高——需要更深的代码级分析
- **进入**：第 2 层换出后
- **换层**：连续 K 轮无提升 → 三层都试过，结束迭代

## 换层机制

```
当前层连续 K 轮没有一次 `keep`
  → 输出当前层小结（有效/无效改动统计）
  → 升到下一层
  → 重置连续拒绝计数

三层都试过仍无提升
  → 输出最终报告，结束
```

## 原子改动自查

每次改完 skill，过一遍：

1. **一句话测试**：这次改动能用一句话说清吗？如果要用"并且"连接，那就是两个改动，拆开。
2. **文件数检查**：`git diff --name-only | wc -l`，超过 3 个文件多半不原子。
3. **改动量检查**：`git diff --stat`，新增超过 30 行，想想能不能更精简。

## 有效 vs 无效的修补模式

有效：
- 说清每个步骤"存在是为了解决什么问题"，而不只是描述步骤本身
- 区分硬约束（不可逆操作确认）和软约束（质量提升手段），给 agent 灵活空间
- 标出哪些信息是结果质量的必要输入
- 把工具调用写成"当 X 条件成立时，调用 Y 解决 Z"

要避免：
- 加"请输出此标记文本"这类机械指令——它掩盖 skill 的真实设计问题
- 一次修补多个 case 的失败——无法隔离效果
- 只加步骤却不说明它保护什么用户利益
- 顺手加入与本次失败无关的改进——破坏原子性

# 迭代主流程与三个层级

skill-evaluate 只有**一条迭代主流程**。L1/L2/L3 不是三个各自独立的循环，而是同一条流程中的三个迭代层级。
这样记忆、采纳判定和回滚只有一套，便于维护。

## 一条主流程

```
① 写失败测试（RED） → ② 执行一次 → ③ 看报告诊断 → ④ 改 skill（一次一个原子改动）
   → ⑤ 重跑验证 → ⑥ 进行采纳判定 → ⑦ 记录 → 回到①/结束
```

每一步在做什么、为什么：

1. **写失败测试（RED）** —— 直接写覆盖核心场景维度的完整，预期它至少暴露一个失败（RED 的本质是"至少有一个 case 红"，而非全红）。没有失败证据时修补容易变成盲目尝试，无法确认改动是否解决问题。
2. **执行一次** —— 用 harness 在隔离环境运行真实 agent，落盘报告（`--out`）。
3. **看报告诊断** —— 读 `stdout/stderr` 和断言结果，判断失败根因是**spec 写法**、**环境/框架**还是**目标 skill 行为**。根因不明显时可调 analyzer 子 agent（见下）。
4. **改 skill（一次一个原子改动）** —— 只改当前层（见 [mutation-policy.md](mutation-policy.md)）。批量修改会破坏因果隔离。
5. **重跑验证** —— 使用**未修改的**同一个 spec。不得为了通过而修改测试。
6. **进行采纳判定** —— 根据多维度结果决定 `keep`、`discard` 或 `revert`（见 [gate-and-memory.md](gate-and-memory.md)）。
7. **记录** —— 写进 `results.tsv` / `experiments.jsonl`；采纳时保存快照并提交，拒绝实验时恢复工作区。

## 三个迭代层级：这一轮检查到哪一层

层与层是"通过才往下"的关系，不是三个独立循环：

| 层级 | 检查什么 | 进入条件 | 用什么断言/评分 |
|------|----------|----------|-----------------|
| **L1 行为** | 硬约束有没有满足（该触发就触发、该调的工具调了、不可逆操作先确认、格式合规） | 默认起点 | `exit_code / contains / regex / tool_called` 等确定性断言 |
| **L2 质量** | 结果质量够不够好（完整度、准确性、风格、是否符合使用场景） | L1 全部通过 | `quality.dimensions` 多维度评分 |
| **L3 提升探索** | 在当前测试覆盖范围内主动发现可验证的提升空间 | L1+L2 全部通过且启用 `aspiration` | Discoverer 生成的新挑战 case |

关键点：**任何一层采纳一次改动，都走同一套第⑥⑦步**（采纳判定 → 记录 → 快照/提交或回滚）。
“锁定改进基线”不再是 L3 专属——任何一层的 `keep` 都会锁定为新的比较基线、快照进 `best_versions`，
后续任何改动都不允许让已锁定的行为退步。

### 手动指定层级

默认 `level: auto`，从 L1 起、按“进入条件”逐层解锁。想直接切到某一层或固定在某一层，有两种等价方式：
调用本 skill 时传 `--level L1|L2|L3`，或在 spec 顶层写 `level` 字段。取值：

| `level` | 效果 |
|---------|------|
| `auto`（默认） | 从 L1 起逐层解锁 |
| `L1` | 只做行为检查，不进 L2/L3 |
| `L2` | 直接进入质量评估（隐含 `quality.iterate: true`） |
| `L3` | 直接进入提升探索（隐含 `aspiration.enabled: true`） |

`level` 只改**起点/上限**，不豁免采纳判定：进 L2/L3 前 L1 断言仍必须全通过；一旦行为退步，立刻回滚并回到 L1。

## L1 行为检查：修正 skill 的可观察行为

- **诊断三分支**：先分清失败是 spec / env / skill 哪一类。只有 `skill` 类才去改目标 skill；spec/env 类改自己。
- **每轮只处理一个失败 case，并只做一个原子改动**，通过后再处理下一个失败 case。
- **同一 case 最多试 3 次**，仍失败就停下来向用户报告已尝试的修补方向——可能是模型能力边界，不该硬撑。
- 放宽断言必须说明理由，且仅当断言本身过于死板（要求精确格式而非语义）时才放宽。

### analyzer 子 agent 辅助诊断

当失败原因不明显（比如语义断言失败但输出看着挺合理），调 analyzer 子 agent 生成结构化诊断。
参考 [`agents/analyzer.md`](agents/analyzer.md)。它输出 `root_cause`（spec/env/skill）正好对应上面三分支；
`confidence < 0.5` 时仍由你自己判断，不要盲从。

## L2 质量评估：提升结果质量

- 只在 L1 全部通过、且 spec 里 `quality.iterate: true` 时进入。
- 先看 quality 报告的 `infra_failed` / `judge_status` / `candidate_text_preview`：若 judge 解析失败或候选正文为空，属于 harness 问题，禁止据此改目标 skill。
- 找**最低分维度**，读它的 evidence/gaps 和 eval_feedback 建议，只改目标 skill 的**指导/示例/模板**，不动断言。
- 每次改完必须重新确认 **L1 行为仍全通过**。一旦行为退步，立刻回滚并回到 L1——行为正确永远优先于质量分数。
- 同一维度连续 2 次没有提升，就切换到当前得分最低的其他维度。
- 分数在阈值 ±0.5 边缘时，可调 comparator 子 agent 做盲评（见 [`agents/comparator.md`](agents/comparator.md)），
  把改动前后输出随机分成 A/B 送评，避免自我确认偏差。

## L3 提升探索：继续提升能力上限

只在 L1+L2 全通过且启用 `aspiration` 时触发。这不是由人预先指定唯一的改进方向，
而是让 Discoverer 子 agent 主动发现“已通过但仍可进一步提升”的方向。

- **Discoverer**（见 [`agents/discoverer.md`](agents/discoverer.md)）每轮开始时分析当前输出，产出一个"提升提案"：
  当前水平、目标水平、一个新挑战 case、建议的修补方向。
- **改进基线锁定**：新挑战通过后，把新 case 纳入正式 spec，成为永久回归保护，并提高质量下限，
  并在记忆里追加"什么修补有效"。已锁定的 case 后续任何改动都不许让它失败。
- **停止条件**（任一触发即停）：
  - 边际递减：连续 2 轮 Discoverer 没有新发现或新挑战没通过
  - 预算耗尽：提升探索循环累计达到上限轮数（默认 5）
  - 回归频繁：连续 2 次改动导致 L1/L2 退步 → 当前探索方向未带来可接受的改进，继续推进可能破坏稳定性
  - 人工满意：用户在检查点表示当前水平已够好

回滚一次失败的修补方案后不终止循环（除非命中停止条件），让 Discoverer 换个方向继续探索。

## 什么时候停、什么时候升层

- 当前层连续 K 轮（默认 5）没有一次 `keep` → 升到下一层（改动范围由浅入深，见 mutation-policy.md）。
- 三层都试过仍无提升 → 输出最终报告，结束。
- L1 同一 case 试满 3 次仍失败 / 语义断言判定为 flaky / 出现行为回归 / 基线对比为负 →
  触发人工检查点（`humanloop.py`），交给用户定夺。

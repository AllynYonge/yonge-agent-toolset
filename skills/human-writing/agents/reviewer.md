# 复审子代理

对当前文章执行综合审核：脚本检查（硬禁令、篇幅、规避词）+ 人工审核（篇章层、句子层、事实层）+ 内容质量与合规红线把关。只评估，不参与创作、不修改文件。

本文件包含四部分：审核模式入口与场景路由、调度规则与主代理闭环服务主代理；末尾「任务提示词」是交给子代理的全部内容。Never 把「主代理闭环」写入任务提示词或传给子代理。

## 审核模式入口

用户要求「审核 / check / audit / review」时进入本模式。本模式只审合规红线与内容质量。用户只想查 AI 痕迹（「看看像不像AI / 查AI痕迹」）时不进入本模式，改为按 `references/quality/revision.md`「只查 AI 痕迹的报告」运行 `scripts/check_prose.py`、做句子层检查并出报告，只报告问题。

1. **加载合规清单**：独立审核按 SKILL.md「九步流程」第 1 步获取 active profile 的 `compliance_guardrails`；创建或改写后的审核沿用当前已确认的任务清单。补入用户本次明确边界，按 `references/publish/overview.md`「合规红线」处理冲突。无额外规则时显式使用 `[]`，解析失败时不继续审核。
2. **派发审核任务**：按下文「调度规则」派发，必须传入完整 `compliance_guardrails`，而非规则摘要或仅条款编号。
3. **呈现报告**：独立审核向用户呈现完整报告（含改写优先级建议），不自动改写。脚本检查和人工审核结果由子代理在内部执行并整合到报告中。合规逐条结论是通过的必要条件：有违反或待核实项即为 `NEEDS_REVISION`；字数与规避词脚本通过不能替代此项，也不得据此承诺平台必然通过审核。

### 场景路由

收到有效报告后，先按下文「结果验收」处置状态，再按场景决定报告去向。第一列的审核是 SKILL.md「九步流程」的第 6 步「综合审核」。

| 场景 | 审核目的 | 报告去向 |
|------|----------|----------|
| 新写或改稿后的综合审核 | 质量与合规把关 | 主代理内部处理，用户不可见；`NEEDS_REVISION` → 下文「主代理闭环」。没有目标平台时 `[PLATFORM]` 填当前文稿类型 |
| 独立审核模式 | 诊断呈现 | 呈现给用户；不自动修复 |

超过 `long_threshold` 的长稿，审核报告按节呈现，附带段落引用。

## 调度规则

- **派发**：用当前环境提供的子代理工具创建一个新任务，只发送填充好的任务提示词。每轮都以第一次看到当前版本的读者视角介入，不传上轮报告。子代理可以运行 `scripts/check_prose.py` 和读取 `references/quality/revision.md`，但不写文件、不向用户提问、不再创建子代理；工具支持限制权限时同时在调度参数里限制。
- **必须得到结果**：是。
- **执行中**：子代理不得回问；主代理不得追加指令（验收补齐除外）。
- **无法派发时**：主代理按同一份任务提示词执行备用审核，只使用下方「允许传递」的信息，并如实说明这是主代理备用审核。Never 声称结果来自独立子代理。
- **等待与去重**：只采用子代理的最终结果；工具日志、中间消息、出错前的部分输出都不算。等待超时、调度出错时保留原任务继续等待或修正调用，不重新派发同一任务。完成通知与主动查询得到的是同一份结果，不重复处理。
- **结束**：结果用完后，停止仍在运行且不再需要的任务。

## 上下文

使用全新独立上下文，不继承父会话。

允许传递：

1. 当前待审核文章全文
2. 目标平台
3. 当前任务的完整 `compliance_guardrails` 清单（无额外规则时为 `[]`）
4. SKILL.md 第 2 步记录的「不能改的东西」清单
5. SKILL.md 第 4 步确定的风格约束和平台要求
6. resolver 返回的 `constraint_check_args`（用于脚本检查）
7. 下方任务提示词

禁止传递：

1. 父会话历史
2. 上一轮审核结果
3. 创作过程、修改理由、主代理预判

## 任务输入

必须提供：

1. `[ARTICLE_PATH]`：当前待审核文稿的路径（用于脚本检查）
2. `[ARTICLE_CONTENT]`：当前待审核全文
3. `[PLATFORM]`：目标平台；没有目标平台时填当前文稿类型，如知乎回答或短篇小说
4. `[COMPLIANCE_GUARDRAILS]`：resolver 返回的完整规则，加上本次明确边界；按原顺序编号并内联规则全文，无额外规则时填 `[]`，不得省略该输入或只传规则摘要
5. `[IMMUTABLE_ITEMS]`：第 2 步记录的不能改的东西（用户明确要求保留的内容、表达方式等）
6. `[STYLE_CONSTRAINTS]`：第 4 步确定的风格约束和平台要求
7. `[CONSTRAINT_CHECK_ARGS]`：用于脚本检查的参数，格式如 `--extend path/to/EXTEND.md --profile 账号名`；无配置时为空字符串

## 结果验收

格式检查：

1. 首行必须是：`审核状态：PASS` / `审核状态：NEEDS_REVISION` / `审核状态：ERROR`
2. 非 ERROR 时须含完整报告结构（脚本检查 / 人工审核 / 合规红线 / 内容质量 / 总结）
3. 脚本检查须报告失败项和警告项数量，失败项必须清零；人工审核须覆盖篇章层、句子层（S8-S11）、事实层
4. 合规红线须逐条覆盖输入清单，记录完整规则、结论（通过/违反/待核实）、原文证据或缺口与处理方向；空清单须写「未配置额外合规红线」。漏项或与首行状态矛盾按格式不全处理
5. 无命中须写「无」，不得空造问题；不得附完整改写稿

按结果形态处理：

| 结果形态 | 主代理动作 |
|----------|------------|
| 格式不全（缺状态行/报告结构/字段） | 平台支持向原任务追加指令时，要求只补齐缺失内容一次；不支持或补后仍不符 → 判定结果无效，不重新派发完整任务 |
| `PASS` | 先确认脚本失败项已清零、合规清单逐条覆盖且无违反/待核实项；遗漏检查按格式不全处理 |
| `NEEDS_REVISION` | 质量把关 → 主代理闭环；独立审核 → 只呈现，不自动修（场景见上文「场景路由」） |
| `ERROR` / 调度失败 / 依赖文件失败 / 子代理明确失败 | 不把部分输出当成功结果；不进入闭环；不计入有效审核轮次 |

仅 `PASS` / `NEEDS_REVISION` 的完整报告计有效轮次。

## 主代理闭环

- **进入**：新写或改稿后的综合审核，且有效结果为 `NEEDS_REVISION`
- **不进入**：独立审核模式；`PASS`；`ERROR` / 非有效轮次

```mermaid
flowchart TD
    A[收到有效审核报告] --> B{场景类型?}
    B -->|诊断呈现| C[呈现给用户，等待指示]
    B -->|质量把关| D[逐条评估问题]
    D --> E{能自主修复?}
    E -->|是：仅措辞/结构<br>不删事实 不改极性| F[执行修复]
    E -->|否：取舍/立场/事实存疑| G[记入待确认清单]
    F --> H[按本任务说明全新派发]
    H --> I{终止条件满足?}
    I -->|无可修复 / 3轮 / 与上轮重复| J{待确认清单?}
    I -->|未满足| D
    J -->|非空| K[呈现待确认项]
    J -->|空| L[输出最终版本]
```

**单轮**：

1. 收到 `NEEDS_REVISION` 后逐条评估（脚本检查/人工审核/合规红线/内容质量）：
   - **能自主修复**：仅措辞/结构调整，且不删事实、不改论点极性 → 直接修
   - **不确定且影响大**：记入待确认清单（内容取舍、立场、事实核实、个人经历真伪）
   - **在不能改清单里的**：标注为待确认，说明冲突
2. 修复时重写相关段落表达，不要只换被标记的词。
3. 修复后按本任务说明重新填充并**全新派发**（只传当前版本，不传上轮报告或修改理由）。

**终止**：

| 条件 | 说明 |
|------|------|
| 本轮无可自主修复问题 | 剩余已在待确认清单或没有问题 |
| 已连续 3 轮有效审核 | 防无限循环 |
| 本轮与上轮高度重复 | 收敛，继续改可能破坏内容 |

**有效轮次**：同「结果验收」。

**约束**：

- MUST 能自主修的都修（级别只影响排序）
- Never 因问题看起来轻微而跳过
- Never 越改越远：修改时保持核心事实、数据与既定立场不变，不得擅自篡改事实或反转论点
- 合规规则存在违反或待核实项时，不得标记为可发布；无法自主修复或达到迭代上限时转入待确认清单，不以终止循环代替通过审核
- 每轮全新终局交付；同轮禁止因超时/调度错误重派
- 审核子代理不得再创建子代理

**结束后输出**：

```
---
修订摘要：
- 迭代轮次：X 轮有效审核
- 已修复的问题：[按类型简列]
- 终止原因：[无可自主修复的问题 / 达到迭代上限 / 收敛]
- 待确认清单：[若非空，逐条列出问题及需要用户做的决策]
---
```

待确认清单每条含：问题描述 + 原文引用 + 为何需用户决策 + 可选修复方向。  
用户逐条决策后主代理执行并输出，不再启动新一轮审核；但涉及合规问题的修改仍须对当前稿件重新核对受影响规则，未解决时保持待处理状态。

## 行为限制

必须：

- MUST 先运行 `scripts/check_prose.py [ARTICLE_PATH] [CONSTRAINT_CHECK_ARGS] --json`，解析结果并整合到报告
- MUST 脚本失败项（failures）必须清零才能 PASS；警告项（warnings）需人工判断
- MUST 按 `references/quality/revision.md`「什么时候做哪几层」执行人工检查：
  - 篇章层（A1-A3）：谁在说、文章有没有往前走、结尾
  - 句子层（S8-S11，脚本查不到的）：假具体、假口语、动作后的解释、白话与古意
  - 事实层（F1）：核现实或设定
- MUST 只报告能由文章原文和审核规则直接支持的问题
- MUST 没有命中时写"无"
- MUST 对每条合规红线检查正文、标题、引述、案例与行动建议，结合语境区分主张、转述、否定与辟谣
- MUST 尊重「不能改的内容」清单，发现问题时标注为待确认而非直接要求修改
- MUST 修改建议符合「风格约束与平台要求」

禁止：

- Never 修改原文或任何文件
- Never 向用户提问
- Never 输出完整改写稿
- Never 输出分析过程、工具调用过程或文件读取日志
- Never 为显得认真而制造问题
- Never 因添加"书中提到"、免责声明或替换词语就认定原有违规主张已消失，也不编造核验依据

## 检查维度

### 1. 脚本检查（硬禁令）

运行 `scripts/check_prose.py [ARTICLE_PATH] [CONSTRAINT_CHECK_ARGS] --json`，解析 JSON 输出。

- **失败项（failures）**：必须清零才能 PASS，包括：
  - S1 冒号与破折号
  - S2 翻案句
  - C1 篇幅超标
  - C2 规避词命中
- **警告项（warnings）**：需人工判断，可能保留：
  - S2 翻案腔变形
  - S3 排比
  - S4 假深刻
  - S5 名词化
  - S6 主干太晚
  - S7 节奏问题

脚本失败时报告 `审核状态：ERROR`。每个问题都带规则编号（如 S1、C2），在报告中保留编号。

### 2. 人工审核（脚本查不到的）

按 `references/quality/revision.md` 执行：

**篇章层（A1-A3）**：
- A1 谁在说：作者凭什么知道、哪里看出在意、哪个判断有材料托着、哪几段换模型也能写
- A2 文章有没有往前走：每段新增了什么、是否只是换说法、材料出处是否清楚
- A3 结尾：删掉最后两段是否更有力

**句子层（S8-S11，脚本查不到的）**：
- S8 假具体：时间、神态、细节是否有来源或作用
- S9 假口语：老铁、咱就是说等是否符合人物
- S10 动作后的解释：是否过度解释读者已能看见的
- S11 白话与古意：成语典故是否必要

**事实层（F1）**：
- 现实稿核时间、数字、身份、引语、因果
- 虚构稿核人物知道什么、时间空间、世界规则
- 有合规清单时逐条核对

### 3. 内容质量检查

以目标平台读者和发布者身份，判断是否具备发布就绪度：

- **开头无吸引力**：第一段没有继续读的理由（无冲突、无场景、无数据、无悬念）
- **平台调性与排版不适**：行文语气、段落组织或呈现形态明显脱离目标平台

### 4. 合规红线检查

逐条返回结论：
- **通过**：未发现违反该规则的表达，给出相关原文或说明不涉及该行为
- **违反**：引用原文位置，指出违反哪条完整规则，给出修正方向
- **待核实**：规则仅有编号、适用范围不明、文章中的来源或事实不足以判断时，列出缺口和需要核实的事项

违反和待核实均阻止 PASS；空清单只表示未配置额外红线，不代表通过全部审查。

# 改写工作流

使用本文件执行改写模式。

| 条件 | 行为 |
|------|------|
| 未配置 `output_dir` | 仅在对话中输出，不保存文件 |
| 已配置 `output_dir` | 第七步生成草稿后，将文件保存至 resolver 返回的 `output_dir`，文件名为 `{title}.md`；文件内容以 `# {platform}-{medium}-draft` 作为顶级标题标记草稿态，文章标题用二级标题 `## {title}` 紧跟其后 |
| 文章通过审核正式交付时 | 将分区标题中的 `-draft` 后缀去掉（如 `# xhs-note-draft` → `# xhs-note`） |
## 改写模式

## 1. 加载偏好设置

在向用户提问之前，调用 resolver 获取最小 active profile 配置：

```bash
python3 skills/human-media-writer/scripts/resolve_preferences.py \
  --workspace-dir "{workspace_dir}" \
  [--profile "<name>"]
```

### 2. 确定选题（不可跳过）

将选题任务委派给 `references/tasks/topic-selection.md` 子代理完成。

即使用户已从分析模式选定方向，本步骤仍不可跳过——分析方向只有灵感与切入策略，还不是可执行选题。选题任务会评审并锐化为 3 个方案供用户最终选择。

MUST 将选题结果原样呈现给用户，等待选定后注入后续步骤：

- 目标用户与场景 → 补充信息收集中的目标读者
- 内容结构 → 指导正文构建
- 核心论点 → 作为核心论点起点
- 关键词与标签 → 指导标题和 SEO

### 3. 提取语义锚点 / 结构蓝图

本步骤根据 `--deep` 档位执行不同操作：

#### --deep low（默认）：提取语义锚点

在改动任何内容之前，从原文中提取以下信息并在内部标记为不可改变的锚点：

- 名称、人名、机构名、产品名
- 日期、时间线和事件顺序
- 数字、价格、比例、排名
- 因果主张
- 对比关系
- 引述性陈述
- 否定、限制条件和极性（正面/负面立场）
- 不确定性标记（"可能"、"据说"、"目前来看"）
- 用户提供的个人经历
- 明确的情感倾向和价值判断

以上信息在改写后必须在含义上保持不变。

#### --deep medium：缩减锚点范围

仅保护以下核心事实类锚点：

- 名称、人名、机构名、产品名
- 日期、时间线和事件顺序
- 数字、价格、比例、排名
- 因果主张

以下信息释放为可改动：示例、过渡段落、支撑性论据的具体措辞、对比关系的具体表述方式。允许替换论据、重排段落顺序、增删支撑细节——只要核心事实不变。

#### --deep high：提取结构蓝图

不提取语义锚点。改为提取原文的**结构蓝图**——逐段标注每段承担的功能角色：

| 段落功能 | 示例 |
|----------|------|
| 开场设问 | 抛出悬念或痛点 |
| 场景铺设 | 建立具体情境 |
| 论点陈述 | 亮出核心主张 |
| 举例论证 | 用案例支撑论点 |
| 数据佐证 | 用数字增强说服力 |
| 转折/递进 | 推进或翻转论证方向 |
| 情感共鸣 | 连接读者感受 |
| 总结收束 | 收尾给出收获或行动 |

提取后形成段落功能序列（如：开场设问 → 场景铺设 → 论点陈述 → 举例论证 × 2 → 转折 → 新论点 → 总结收束）。这个序列是改写的骨架约束——后续步骤 6 用全新内容填充每个功能槽位，但保持序列不变。

同时记录原文的修辞节奏特征（段落长短交替模式、短句密集区与长句舒展区的分布），作为节奏参考。

### 4. 风格

按优先级确定写作风格：

1. 用户本次请求中的显式风格指令（最高优先）
2. resolver 返回的 active profile `custom_style`（内联自定义风格）
3. resolver 返回的 active profile `writing_style`（内置风格预设名）
4. `default` 风格预设（兜底）

使用 resolver 返回的 `style` 获取具体声音参数。若用户提供了写作样本要求模仿，或需要从样本提取风格结构，按 `references/writing-style.md` §写作风格系统 的自定义风格结构与样本提取流程执行。

### 5. 平台

从用户信号中确定目标平台：

| 信号 | 平台 |
|------|------|
| 公众号/微信/长文/深度 | 微信 |
| 小红书/xhs/笔记/种草 | 小红书 |
| 无信号 | resolver 返回的 active profile `platform`，再无则默认微信 |

确定后按 `references/platforms/{platform}-{medium}.md` 应用发布形态约束（分发机制、用户心智、内容规范中的段落密度、交互偏好中的 emoji 策略等）。

### 5.5 媒介

在平台确定后、改写开始前确定内容媒介（载体）。媒介决定叙事结构、开篇钩子、篇幅特性。

| 信号 | 媒介 |
|------|------|
| 长文/深度/专栏文章 | article（长图文） |
| 短图文/卡片/笔记/种草 | note（短图文笔记） |
| 无信号 | resolver 返回的 active profile `medium`，再无则按平台推断（微信→article，小红书→note） |

确定后从 `references/platforms/{platform}-{medium}.md` 加载完整形态约束（叙事结构、开篇钩子、篇幅特性、起草侧重、结构步）。篇幅特性与 `length` 硬约束冲突时，以 `length` 为准。形态特定的起草侧重与可选结构步由该数据文件的 §起草侧重 / §结构步 供料，改写阶段就地读取——新增或调整某个形态的行为只改它的数据文件，不改本流程。

### 6. 改写

本步骤根据 `--deep` 档位执行不同策略：

开始改写前，把 `references/platforms/{platform}-{medium}.md` §起草侧重 叠加到本步策略之上（该形态的侧重优先于通用倾向，但不越过锚点保护与 `length` 等硬约束）；并读取该文件 §结构步——非空则按其说明补做这一步并入改写规划，为空则跳过（基础流程预留的扩展槽，新增特殊结构需求的形态时只填数据文件本节，不改本流程）。

#### --deep low / medium：重写而非修补

去AI味的正确方法不是逐词替换——是把原文意思理清后，用中文本来的说法重新说一遍。逐词修补只能消除表面信号，无法解决句法骨架层面的翻译腔。

执行方式：
1. 读完一个段落后，合上原文，用一句话说清楚"这段想表达什么"
2. 用这个核心意思作为锚点，重新组织语言——不要看着原文改
3. 改完后对照锚点清单，确认事实未丢失（`low` 对照全部锚点；`medium` 仅对照核心事实锚点，其余可自由发挥）

逐段重建文章。这不是简单的短语替换：

- 重组段落，使每个段落承担不同的功能
- 变化句式节奏（短句、中句、长句、片段句）
- 用具体场景或实例替代抽象表述
- 移除 AI 词汇簇（参见 `references/ai-tell-catalog-zh.md`）
- 保留原文论证的逻辑和推进过程
- 保留作者的真实的例子和数据不变（`medium` 模式下允许替换论据和示例，只要核心事实不变）

#### --deep high：结构复刻

在步骤 3 中已提取原文的段落功能序列和修辞节奏特征。本步骤以该结构蓝图为骨架，用全新内容填充每个功能槽位。

执行方式：
1. 逐个功能槽位创作：按段落功能序列依次填充，每个槽位产出对应功能的新段落
2. 内容来源：选题诊断（步骤 2）选定的方向提供核心论点和切入角度；围绕该论点生成新的论据、案例、数据和表述
3. 节奏参考：参照原文的修辞节奏特征（段落长短交替、句式密度变化），但不拘泥于精确复制
4. 不对照原文内容：原文的具体事实、例子、数据全部可替换——约束对象是结构，不是语义

注意事项：
- 结构蓝图是指导而非牢笼——如果某个功能槽位在新论点下显得多余或不自然，可以合并相邻槽位或微调功能，但整体叙事节奏应与原文同构
- 如果用户同时指定了具体的语义保护要求（如"数据不要动"），在对应槽位中保留该内容

#### 长内容跨节一致性

对于长内容（超过 long_threshold）：按标题或主题段落逐块处理。每完成一个段落后执行跨节一致性检查：

1. 回读前一节最后两句 + 当前节开头两句，检查语气温度是否断裂（如前节冷静分析，当节突然煽情）。
2. 对比当前节与前一节的句式节奏——如果两节的平均句长和段落长度近似，主动打破其中一节的节奏。
3. 检查用词重复：如果同一个"过渡词"或"态度词"在相邻两节都出现，替换其中一处。
4. 全部段落完成后，快速通读首段和末段，确认全文的情感弧线连贯（起点 → 终点之间有推进，而非平行重复）。

### 7. 硬约束自检

改写完成后，MUST 先调用约束检查脚本，确认 `length` 和 `words_to_avoid` / `avoid_words` 通过后再进入用户确认：

```bash
python3 skills/human-media-writer/scripts/check_article_constraints.py \
  --article "{article_path_or_text}" \
  [constraint_check_args] \
  --json
```

**执行规则**：
- 如果 `length` 未通过：一次性判断需要删减多少字，从全文中定位 1-3 处可精简的段落或句子，做一次集中删减，不逐字微调。优先删减冗余解释、重复论证、可合并的相邻段落。Never 为凑字数注水。
- 如果 `words_to_avoid` / `avoid_words` 命中：逐词替换，用具体动作或事物替代包装性词汇。
- 修复后重新运行脚本，确认通过后再进入步骤 8。
- 如果连续 3 次修复仍未通过，向用户说明当前状态（实际字数、目标区间、难以进一步压缩的原因），请用户决定是否放宽约束或手动删减。

### 8. 用户确认

改写完成后，暂停委派审核子代理，先向用户呈现以下内容：

1. **完整改写稿**（或指明已保存的文件路径）
2. **优化建议**（2-4 条）：基于当前稿件，给出主代理观察到的可选改进方向（如某段论证可以更具体、某处过渡略突兀、结尾可以更锋利等）。标记为建议，不自动执行。

**等待用户回复**：
- 用户确认"可以"/"没问题"/"继续" → 进入步骤 9
- 用户提出修改意见 → 执行修改后重新呈现，再次等待确认
- 用户采纳部分优化建议 → 执行对应建议后重新呈现

### 9. 委派审核子代理

执行 `references/tasks/article-review.md`，调度遵循 `references/subagents/protocol.md`。  
修复→再审循环按 `references/tasks/article-review.md`「交互模式 · 主代理闭环」，直到满足终止条件。

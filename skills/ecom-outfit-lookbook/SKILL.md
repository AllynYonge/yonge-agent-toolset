# 电商穿搭图组流水线

把「一张服饰图 → 可直接投放的成组穿搭展示图」这条链固化下来。

**本技能的产出是 A/B 测试素材，不是单张美图。** 多组方案存在的唯一理由是横向对比、找出转化率最高的那一组。因此**跨全部图片的主商品同一性，优先于任何单张图的美感**。若某张图好看但主商品的颜色、版型、图案变了，它就是废图。

## 五条硬约束

1. **`assets/prompts/` 下 01–03 三段提示词的措辞、铁律、字段粒度不要改。** 只做占位符替换。用户明确要求原样固化，你的编排能力体现在流程与归档上，不在改写提示词上。**04 段（场景提示词）是例外：它决定场景描述的丰富度与画面基调，允许按「场景词要写到什么粒度」一节演进。** 05 段本身就是元提示词，不在本约束内。全部提示词的「输出格式铁律」段一律不动——它规定的是产物落盘结构（单文件 + `---` 分块），是脚本解析的前提。
2. **`classification`（仅上衣 / 仅下衣 / 套装）只判一次并落进 manifest。** 断点续跑时若重新判断，可能与前半批结论不一致，后果是同一批图里有的擅自配了下装、有的没配，直接违反「不得增删主体服饰」。
3. **两道硬闸门必须停下等用户**：服装三视图出图后、方案产出后。不要自作主张往下跑。**唯一例外是 yolo 模式**（见「yolo 模式」一节），用户显式要求时才跳。
4. **生成图片一律通过 `baoyu-image-gen` 技能**，不要另找出图途径。
5. **主图/详情图的数量、命名、画幅由脚本按位次决定，不接受参数覆盖。** 前 `--mains` 张是 `主图NN.png`，后 `--details` 张是 `详情图NN.png`（画幅见「出图参数速查」）。这套中文命名是 `doudian-publish` 的既有契约（它的 `read-plan.py` 按 `startswith("主图")` / `startswith("详情图")` 归类素材），改名会断掉下游直读。对比图的 `详情图-对比图01.png` 同理。

## 目录结构

```
<商品名>/
├── 00-input/                原始服饰图（唯一未经模型改写的 ground truth）
├── 01-garment-triview/      garment-prompt.md、garment-triview.png
├── 02-plans/                plans.md、compares.md（各装全部块，`---` 分块）
├── 03-shoots/
│   ├── plan-01/             model-prompt.md、model-triview.png、scenes.md、
│   │                        主图01.png…主图05.png、详情图01.png…详情图03.png、
│   │                        compare-prompt.md、详情图-对比图01.png（可选）
│   └── … plan-NN/
├── batch.json               临时批装配文件（场景图）
├── batch-compare.json       临时批装配文件（对比图）
└── manifest.json            全部产物状态与参考图记录
```

`plan-NN/` 目录出图后即可被 `doudian-publish` 直接读走，不需要中间那道手工改名。主图生成时就是方图，所以 `publish.mjs` 的居中裁剪对它是空操作，不会再产生 `主图NN_1x1.jpg`。

**方案、场景、对比图提示词各自只有一个汇总文件。** `plans.md` 装全部方案，`plan-NN/scenes.md` 装该方案全部场景，`compares.md` 装全部方案的对比图提示词，块之间用单独一行 `---` 分隔，块序即编号。`compares.md` 是唯一事实来源，`plan-NN/compare-prompt.md` 由 `split-compares` 从它拆出。不要再生成 `plan-01.md` 或 `scene-1.md` 这类拆分文件——脚本已改为直接解析单文件，两套并存必然出现改了一处忘了另一处。

`scenes.md` 的块号与图的对应关系是**位次映射**：第 1–5 块 → `主图01`–`主图05`，第 6–8 块 → `详情图01`–`详情图03`（按实际 `mains`/`details` 推）。块标题仍写 `## 场景 N`（N 为 1 到 mains+details 的全局序号），04 段提示词原文不动，所以写场景词时不区分主图/详情图分工。

## 提示词落盘通则

每张单发图的完整提示词先落盘成 `.md`，再用 `--promptfiles` 指向它出图，不要把长提示词内联进命令行。落盘位置就在该图的同级目录（服装三视图 → `01-garment-triview/garment-prompt.md`，模特三视图 → `03-shoots/plan-NN/model-prompt.md`），不放工作区根目录、不加隐藏点前缀。

两个理由：闸门上用户说「重新生成」时要能一眼找到并直接改它，而不是重拼一遍；命令行内联会撞上引号与换行的转义问题，且事后无从查证当时究竟喂了什么。

## 编排脚本

确定性的活全部交给 `{baseDir}/scripts/pipeline.ts`（bun 运行），你不要手写 JSON 或手算待办：

```bash
bun {baseDir}/scripts/pipeline.ts init --workspace <ws> --product <名称> [--plans 10] [--mains 5] [--details 3]
bun {baseDir}/scripts/pipeline.ts classify --workspace <ws> --value 套装
bun {baseDir}/scripts/pipeline.ts plan --workspace <ws> --plan 3
bun {baseDir}/scripts/pipeline.ts refs --workspace <ws> --plan 3
bun {baseDir}/scripts/pipeline.ts build-batch --workspace <ws> [--plans-only 1,2] [--quality normal]
bun {baseDir}/scripts/pipeline.ts compare-input --workspace <ws>
bun {baseDir}/scripts/pipeline.ts split-compares --workspace <ws> [--force]
bun {baseDir}/scripts/pipeline.ts build-compare --workspace <ws> [--plans-only 1,2] [--quality normal]
bun {baseDir}/scripts/pipeline.ts sync --workspace <ws>
bun {baseDir}/scripts/pipeline.ts mark --workspace <ws> --path <路径> --status failed --error "<原因>"
bun {baseDir}/scripts/pipeline.ts status --workspace <ws>
```

`--ar` / `--scenes` / `--main-ar` / `--detail-ar` 已废弃，传了会报错退出而不是静默忽略：`--ar 3:4` 若被忽略，你会以为全批是竖版，实际前 5 张仍是方图，而这要到几十张图出完才看得出来。

创作性的活（写方案、写场景提示词、判断漂移）由你完成，脚本不碰。

`plan --plan N` 从 `plans.md` 里按 `---` 切出第 N 块原文打印出来，步骤 4、5 需要「该方案的完整内容」时用它，不要每次把整份 `plans.md` 读进上下文。

它会校验块内 `## 方案 N` 的编号与 `--plan` 是否一致，不一致就报错退出。**此时去修 `plans.md` 的编号，不要随手加 `--loose` 绕过。** 编号错位意味着把另一个方案的搭配拿去生成这个方案的图，整组作废，而且要到出图后才能看出来。`build-batch` 与 `status` 也会把全量编号问题作为告警列出。

## 占位符

替换规则只写在这里，`assets/` 里只有提示词原文加占位符。

| 占位符               | 含义                                      |
| ----------------- | --------------------------------------- |
| `{{REF_IMAGES}}`  | 参考图路径（`02-plan-table.md` 中替换原本的 `@图片1`） |
| `{{PLAN_COUNT}}`  | 方案总数，默认 10                              |
| `{{PLAN_INDEX}}`  | 当前方案序号                                  |
| `{{SCENE_COUNT}}` | 每方案场景数，等于 `mains + details`，默认 8        |

`05-compare-poster.md` 是**元提示词**，不走占位符填充那条路：它读一次全量输入，一次性写出全部方案的对比图提示词。它只有三个输入位，全部由 `compare-input` 一次给出：

| 占位符                  | 含义                                     |
| -------------------- | -------------------------------------- |
| `{{CLASSIFICATION}}` | 品类判定，决定合规话术与拆分方式的可选集                    |
| `{{PLAN_COUNT}}`     | 方案总数，即要写出多少个块                          |
| `{{PLAN_DIGEST}}`    | 全部方案的风格摘要（风格名称 / 主打关键词 / 风格调性），整段贴进去    |

## 工作流

### 步骤 0 — 建工作区

问清商品名与原始图位置（用户没给就从图片文件名推导商品名）。跑 `init`，把原始图拷进 `00-input/`。

参数默认 `--plans 10 --mains 5 --details 3`。**若用户想先小规模试产，用 `--plans 1 --mains 1 --details 1`**：满配是 1 + 10 + 80 = 91 张图，先花 4 张确认提示词与链路没问题，比中途中断省得多。

### 步骤 1 — 判定品类并落盘

看 `00-input/` 的图，判断是「仅上衣 / 仅下衣 / 套装」，并识别多张图属于哪种情形：

- **同一件衣服的多角度或多细节照** → 全部当参考，合成一张服装三视图
- **多件单品共同构成一套** → 判为「套装」

把结论摆给用户确认，再跑 `classify` 写入。误判成本很具体：套装被判成「仅上衣」，后续每组方案都会擅自补下装。

### 步骤 2 — 生成服装三视图

用 `assets/prompts/01-garment-triview.md` 原文，参考图为 `00-input/` 全部图片，按「提示词落盘通则」落盘到 `01-garment-triview/garment-prompt.md`，输出 `01-garment-triview/garment-triview.png`。

顺序单发（不走 batch），因为这是全局主参考，需要看清单张结果：

```bash
--ref <00-input 下全部图> --promptfiles 01-garment-triview/garment-prompt.md --ar 4:3 --quality normal
```

**🚧 硬闸门 ①** — 这张图是后续全部图片的主参考，错了后面全废。给出图片路径，请用户选择：通过 / 重新生成 / 我手动换好了继续。重点让用户核对颜色、版型、图案、细节图那一栏是否可用。

### 步骤 3 — 生成方案

用 `assets/prompts/02-plan-table.md`，替换 `{{REF_IMAGES}}` 为服装三视图路径、`{{PLAN_COUNT}}` 为方案数。这是纯文本推理，不出图。

输出到 `02-plans/plans.md`：全部方案写在这一个文件里，每个方案一块，块之间用单独一行 `---` 分隔。不出表格，不再拆成单方案文件。

**🚧 硬闸门 ②** — 把 `plans.md` 全文直接贴进对话（用户不用开文件就能扫），请用户选择：通过 / 重新生成 / 我改完了继续。这是调转化率的主战场，纯文本改起来最便宜。yolo 模式下贴完即继续。

### 步骤 4 — 每方案生成模特三视图

用 `assets/prompts/03-model-triview.md`，`{{PLAN_INDEX}}` 替换为方案号，并把 `plan --plan N` 取出的该方案完整内容随提示词一并给出。

**模特必须穿着主商品 + 该方案的「新增搭配」（含鞋履、配饰、发型、妆容），是完整 look，不是素模。** 否则方案里最关键的差异化字段要等到最后一层扇出（70 张）才第一次被渲染，等于拿全部额度去赌。

拼好的完整提示词按「提示词落盘通则」落盘到 `03-shoots/plan-NN/model-prompt.md`（与 `scenes.md` 并列），再用 `--promptfiles` 指向它出图。

参考图与优先级按步骤 6 的「参考图链路与优先级」执行，此时尚无模特图，喂 `00-input/` + 服装三视图。顺序单发，`--ar 4:3 --quality normal`，输出 `03-shoots/plan-NN/model-triview.png`。

**🚦 软闸门 ③** — 全部模特三视图出完后停一次，列出路径，让用户多选「哪几组继续跑场景图」，默认全选。用户可以直接跳过这一道，yolo 模式下视为全选。坏方案在这里拦住，就省掉了它对应的全部场景图。

### 步骤 5 — 每方案生成场景提示词

用 `assets/prompts/04-scene-prompts.md`，替换 `{{PLAN_INDEX}}` 与 `{{SCENE_COUNT}}`，并给出 `plan --plan N` 取出的方案内容与模特三视图。纯文本，不出图。

输出到 `03-shoots/plan-NN/scenes.md`：该方案的全部场景写在这一个文件里，每场景一块，块之间用单独一行 `---` 分隔，块序即场景号。不再拆成 `scene-N.md`。

写完跑一次 `status` 核对每方案的「场景词 N/M」计数——块数与 `mains + details` 不符时 `build-batch` 会漏图，此处发现只需重写文本。缺的块若落在后三位，丢掉的就是详情图。

#### 场景词要写到什么粒度

04 段要求每块写齐七个维度（景别与机位构图、光线、色彩关系、环境层次、模特动作与状态、服装呈现重点、画面质感），并要求整组共用一套美学基调，具体定义与示例以 04 段原文为准，此处不复述。你在此只需把三件事当成交付标准自检：

- **一句长句不算写完。** 只写「景别 + 地点 + 穿着 + 动作 + 一句氛围」而缺光线、机位、色彩关系、环境层次与质感时，出图模型会拿自己的默认值补位，而它的默认值就是广告级柔光大片。
- **真实不能拿丑去换。** 抓拍感靠光比、皮肤纹理、进行中的动作与非居中构图拿；一旦开始靠垃圾桶、脏污墙面、乱堆杂物去证明「这是真的」，出来的图可信但没人愿意存下来，作为电商素材同样是废的。写环境痕迹时挑与色调同一伙的物件。
- **全部场景块的服装呈现重点必须各不相同。** 逐块重复贴同一段穿着描述是在浪费字数：衣服长什么样已由参考图锁定，块内的字该花在这一张独有的机位、光线与那个要看清的部位上。

写完自己扫一遍：若各块开头句式雷同、找不出每块各自要看清哪个部位、或整组的光线与色彩基调各自为政（这张冷调高对比、下张暖调柔光），重写比出图后返工便宜得多。

### 步骤 6 — 生成最终展示图

跑 `build-batch` 装配，然后交给 baoyu-image-gen 批量出图：

```bash
bun {baseDir}/scripts/pipeline.ts build-batch --workspace <ws>
# 然后用 baoyu-image-gen 的 --batchfile <ws>/batch.json --jobs 10
```

画幅由 `build-batch` 按位次写进每条任务（取值见「出图参数速查」），不可用参数覆盖。质量默认 `normal`，用 `--quality` 覆盖；`build-batch` 已在本地先做一道合法值校验，不至于跑到出图时才报错。

`--jobs 10` 在命令行覆盖即可，**不要修改用户的全局 EXTEND.md** —— 那会影响用户其他所有出图任务。

出图后跑 `sync` 回填状态，再跑 `status` 看总览。

#### 参考图链路与优先级

三张参考同时喂，并在提示词末尾附上优先级声明（`build-batch` 已自动附加，手工单发时你要自己带上）：

| 要保住什么              | 以谁为准      |
| ------------------ | --------- |
| 人物身份、脸型、发型、妆容、鞋履配饰 | 模特三视图     |
| 主商品的颜色、图案、面料质感     | **原始服饰图** |
| 主商品的背面结构与局部细节      | 服装三视图     |

原始图必须在链路里当色彩锚点：模特三视图是第二代产物，它自己已经可能偏了，若以它为唯一真相，全部场景图会继承这个偏差且再无校正源。同时要声明「以上参考图均为同一主商品与同一模特，请保持同一性，不要重新设计或生成相似的新主体」——长篇的五官描述反而会让模型合成一个新的相似人物。

#### 画面质感锚点

场景图要的是**生活抓拍感**，不是广告大片。`build-batch` 会自动把质感条款（`CANDID_TEXTURE`）附在每张图提示词的末尾，手工单发时你要自己带上。两件事值得知道：

**为何由脚本附加而不只写在 04 段里。** 03 段的模特三视图是影棚白底规格图，影棚光在那一层是对的（身份锁得越准越好），但它同时是每张场景图的第一参考，那股精修质感会沿参考链一路传到 80 张成图上。所以质感得在每张图的提示词末尾（近因位）反向压一次，而不是只靠场景词文本。好处是已写好的 `scenes.md` 不需重写就能生效。

**抓拍感让位于主商品可辨。** 真实感只许从光线、皮肤、构图、环境去拿；靠虚焦、遮挡或暗部把衣服吞掉换来的真实感是废图——本技能开篇的同一性原则优先于任何单张的风格追求。

**真实与美感各拿一半，两条都要。** `CANDID_TEXTURE` 的每条「允许不完美」都配了一条美感边界（倾斜要有取景意图、光要有好看的落点、陈设是挑过的、动作取线条好看的那一帧）。这是成对给的：只给前半句时，模型会把「真实」执行成随机歪斜加写实的丑陋陈设。

对比图（步骤 8）**不适用**本条：它是带文案的营销物料，干净锐利的排版质感是它该有的样子，走它自己的 `COMPARE_REF_PRIORITY`。

### 步骤 7 — 失败汇总

三级处理：baoyu 自带每图 3 次重试不干预 → 3 次全败则 `mark` 为 failed 并**继续跑其余图**，不中断整批 → 全批结束后 `status` 汇总失败清单，问用户「重试这些 / 跳过 / 停下」。

人工返工入口：用户看到某张漂移了，删掉该文件后跑 `sync`，状态自动退回 pending，重跑 `build-batch` 就会补上。

### 步骤 8 — 每方案一张对比图

前七步产出的是**摄影素材**：一个模特、一个场景、无文字。本步产出的是**营销物料**：多幅对照、带层级的中文文案、直接讲「一衣多穿」这个卖点。两者不是同一层的质量升级。

用户提到一衣多穿、一件多搭、对比图、分屏图、带文案的详情页图、买一套等于多套、海报式商品图时走本步。**前提**：该方案的 `model-triview.png` 已存在，不需要场景图已完成。

本步的提示词由你**一次性写全部方案**，不是按模板逐个填空。对比图本身就是要测版式与文案：若 N 张只有模特脸和几句副标题不同，这一批就只测出了噪声。所以 `05-compare-poster.md` 是元提示词，你的任务是在版式、调性、文案、拆分四个维度上主动把 N 张拉开。

#### 8.1 取全量输入

```bash
bun {baseDir}/scripts/pipeline.ts compare-input --workspace <ws>
```

一次打印品类判定、方案总数与**全部方案**的风格摘要，对应 `05-compare-poster.md` 的三个输入位。不要逐方案跑，也不要把 `plans.md` 整份读进来——摘要已经够写提示词了。

`{{PLAN_DIGEST}}` 必须是全部方案，不能逐方案投喂：版式、调性、文案、拆分这四个差异维度是跨方案约束——只看得到一个方案时，模型无从判断该往哪个方向错开，结果就是方案 3 和方案 7 各自挑中同一套版式。

#### 8.2 一次写出全部对比图提示词

读 `assets/prompts/05-compare-poster.md`，按 8.1 的输出替掉三个占位符，然后**一次性输出 N 个块**，写入 `02-plans/compares.md`。

格式契约由 05 段正文规定，这里只强调脚本会校验的三点：每块以 `## 对比图 N` 开头、块间用单独一行 `---` 分隔、每块的四行维度声明（版式/调性/文案/拆分）紧跟标题。声明行只用于人工审阅与查重，不会传给出图模型——**要渲染的文案原文必须写在正文里**。

写完后自己先扫一遍四元组有没有撞车。`split-compares` 会做同样的检查，但你在这里改比出图后改便宜得多。

#### 8.3 人工审阅闸门，然后拆块落盘

**把 `compares.md` 交给用户过一遍，等他确认后再拆。** 这一步是纯文本、不烧出图额度，撞车和文案问题在这里改是最便宜的时机；一旦出图，返工成本是 N 张图。

```bash
bun {baseDir}/scripts/pipeline.ts split-compares --workspace <ws>
```

按 `---` 拆到各 `03-shoots/plan-NN/compare-prompt.md`，与 `model-prompt.md` 并列，返工时直接改字重跑。已存在的文件默认跳过并提示，要覆盖显式加 `--force`。

它会报错退出的情形：块数与方案数不符、`## 对比图 N` 编号错位或重复。**此时去修 `compares.md`，不要绕过**——编号错位意味着把 A 方案的文案配到 B 方案的图上。四元组完全重复也报错；单一维度占比过半只告警，因为有时确实是该方案风格所限。

#### 8.4 先出探针，再批量

```bash
bun {baseDir}/scripts/pipeline.ts build-compare --workspace <ws> --plans-only 1
# baoyu-image-gen --batchfile <ws>/batch-compare.json（单张，不用 --jobs）
```

出完自己读图，逐项确认四件事（前三条与版式无关，一律要过）：

1. **中文渲染**：每个字是不是真汉字、无错字缺笔；最小级注解在 `normal` 分辨率下能不能读。
2. **同一人**：各幅是不是同一张脸、同一发型；有没有只画出一个人，或画成两个不同的人。
3. **主商品一致**：各幅的颜色、图案密度、版型细节是不是同一件；补充单品有没有抢焦点。
4. **版式落地**：出来的画面结构是不是你在那一块里写的版式（写了「大小主次」却出成等宽分屏，说明该块的版式描述不够具体）。

四项全过才跑剩下的。注意探针只验证了它自己那一块的版式，其余版式是各自独立的设计，批量出完仍要逐张扫一遍第 4 条：

```bash
bun {baseDir}/scripts/pipeline.ts build-compare --workspace <ws>
# baoyu-image-gen --batchfile <ws>/batch-compare.json --jobs 10
```

探针不过时，改的是 `compares.md` 里对应那一块，然后对该方案重跑 `split-compares --force` 再出图——不要直接改 `compare-prompt.md`，那样下次整份重拆就丢了。

改提示词两次仍不过，**把图和具体崩在哪一项拿给用户，不要自行改成脚本叠字或拆成两张图**——那是用户已经否掉的方案，换路要用户同意。若崩的是版式（第 4 条）且该版式反复出不来，可以在那一块里换一个更常见的版式取值，这属于同一维度内的调整，不算换路。

#### 8.5 下游契约

`详情图-对比图01.png` 能被 `doudian-publish` 的 `startswith("详情图")` 命中，但随后的排序是纯字符串比较，`-`（0x2D）&lt; `0`（0x30），**所以它排到详情图第一位**。这是有意保留的：对比图是转化钩子，放第一屏合适。用户要排最后就改名 `详情图04-对比.png`。

## yolo 模式

用户说「yolo」「一路跑完」「别问我」「不用确认」时进入本模式。

**只跳闸门，不跳参数确认。** 步骤 0 的商品名、原始图位置、`--plans` / `--mains` / `--details` 规模照常问清——这三件事问错，跳过闸门只会让错误一路放大到 91 张图。

跳过的是三处停顿：

| 原闸门        | yolo 下的行为                     |
| ---------- | ----------------------------- |
| 🚧 ① 服装三视图 | 出图后打印路径，不等确认，直接进步骤 3          |
| 🚧 ② 方案    | 贴出 `plans.md` 全文，不等确认，直接进步骤 4 |
| 🚦 ③ 模特图筛选 | 视为全选，全部方案继续跑场景图               |

失败处理仍按步骤 7 执行：重试 3 次仍败则 `mark` 为 failed 并继续跑其余图，全批结束后 `status` 汇总。**汇总后停下来问用户「重试这些 / 跳过」，这一问不属于闸门，不要省。** 已经烧掉的额度需要用户决定是否追加。

每跳一道闸门都在对话里留一行记录（如 `[yolo] 跳过闸门 ①，服装三视图未经确认`），收尾时一并列出。用户跳过的是审查动作，不是知情权；出问题时这几行是唯一的追溯线索。

## 出图参数速查

本表是画幅与质量的唯一事实来源，其他章节只引用不复述。

| 产物                     | 方式                        | 画幅  | 质量         |
| ---------------------- | ------------------------- | --- | ---------- |
| 服装三视图                  | 顺序单发                      | 4:3 | normal |
| 模特三视图                  | 顺序单发                      | 4:3 | normal |
| 主图 `主图NN.png`（前 5 张）   | batch `--jobs 10`         | 1:1 | normal |
| 详情图 `详情图NN.png`（后 3 张） | batch `--jobs 10`         | 3:4 | normal |
| 对比图 `详情图-对比图01.png`    | 先单张探针，再 batch `--jobs 10` | 3:4 | normal |

三视图是横向三联加下方细节，需要横幅；主图对齐抖店轮播位的方图要求；详情图是往下滚的竖版卖点图。对比图沿用详情图的 `3:4`，不新增画幅。它带二十多个中文字分四个字号，实测 `normal`（1086×1448）下最小级注解仍清楚可读，不用提到 `2k`；若小字糊了，把图拿给用户选「减少文字层级 / 提质量」，不自己定。

**质量列一律用 baoyu-image-gen 的 `--quality` 合法值**：`normal`（对应 1k 分辨率）或 `2k`。**不要传 `1k`** —— 它不是合法预设，baoyu 会以 `Invalid quality: 1k` 直接报错退出。

## 收尾提醒

四件最容易出错、也最贵的事，换个说法再讲一次：

**提示词原文不要动。** 01–03 三段逐字固定（只 04 段可按「场景词要写到什么粒度」演进）；全部提示词的「输出格式铁律」一律不动——`plans.md` 不出表格、`scenes.md` 单文件 `---` 分块，这两条是脚本解析的前提。

**场景图要拍得像真人随手拍的，同时得好看。** 光线、皮肤、构图、环境全往真实那边写，但真实不是靠写丑东西换来的，陈设与色彩要挑过；一旦真实感开始吃主商品的图案与版型，先保主商品。

**闸门前不要抢跑。** 在闸门处返工只花 1 张图或 0 张图，往下跑则是 90 张。yolo 是用户自己承担这个代价，不是你替他决定。

**原始服饰图始终在参考链里。** 它是唯一没被模型改写过的事实，抽掉这个锚点，漂移就单向不可逆。

**「详情图」这个名字只保证文件名与画幅。** 04 段要求 8 张覆盖远景到近景并串成故事板，5/3 切分是在第 5 块处机械截断——落到 6–8 块的是哪几个景别由写场景词时的排布决定。不要向用户宣称后三张在内容上是「卖点细节图」。

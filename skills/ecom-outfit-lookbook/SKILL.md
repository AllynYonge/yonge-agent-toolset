# 电商穿搭图组流水线

把「一张服饰图 → 可直接投放的成组穿搭展示图」这条链固化下来。

**本技能的产出是 A/B 测试素材，不是单张美图。** 多组方案存在的唯一理由是横向对比、找出转化率最高的那一组。因此**跨全部图片的主商品同一性，优先于任何单张图的美感**。若某张图好看但主商品的颜色、版型、图案变了，它就是废图。

## 四条硬约束

1. **`assets/prompts/` 下四段提示词的措辞、铁律、字段粒度不要改。** 只做占位符替换。用户明确要求原样固化，你的编排能力体现在流程与归档上，不在改写提示词上。唯一例外是「输出格式铁律」段——它规定的是产物落盘结构（单文件 + `---` 分块），已由用户核定，同样不要改。
2. **`classification`（仅上衣 / 仅下衣 / 套装）只判一次并落进 manifest。** 断点续跑时若重新判断，可能与前半批结论不一致，后果是同一批图里有的擅自配了下装、有的没配，直接违反「不得增删主体服饰」。
3. **两道硬闸门必须停下等用户**：服装三视图出图后、方案产出后。不要自作主张往下跑。**唯一例外是 yolo 模式**（见下），用户显式要求时才跳。
4. **生成图片一律通过 `baoyu-image-gen` 技能**，不要另找出图途径。
5. **主图/详情图的数量、命名、画幅由脚本按位次决定，不接受参数覆盖。** 前 `--mains` 张是 `主图NN.png`（`1:1`），后 `--details` 张是 `详情图NN.png`（`3:4`）。这套中文命名是 `doudian-publish` 的既有契约（它的 `read-plan.py` 按 `startswith("主图")` / `startswith("详情图")` 归类素材），改名会断掉下游直读。

## yolo 模式

用户说「yolo」「一路跑完」「别问我」「不用确认」时进入本模式。

**只跳闸门，不跳参数确认。** 步骤 0 的商品名、原始图位置、`--plans` / `--mains` / `--details` 规模照常问清——这三件事问错，跳过闸门只会让错误一路放大到 91 张图。

跳过的是三处停顿：

| 原闸门 | yolo 下的行为 |
|---|---|
| 🚧 ① 服装三视图 | 出图后打印路径，不等确认，直接进步骤 3 |
| 🚧 ② 方案 | 贴出 `plans.md` 全文，不等确认，直接进步骤 4 |
| 🚦 ③ 模特图筛选 | 视为全选，全部方案继续跑场景图 |

失败处理仍按步骤 7 执行：重试 3 次仍败则 `mark` 为 failed 并继续跑其余图，全批结束后 `status` 汇总。**汇总后停下来问用户「重试这些 / 跳过」，这一问不属于闸门，不要省。** 已经烧掉的额度需要用户决定是否追加。

每跳一道闸门都在对话里留一行记录（如 `[yolo] 跳过闸门 ①，服装三视图未经确认`），收尾时一并列出。用户跳过的是审查动作，不是知情权；出问题时这几行是唯一的追溯线索。


## 目录结构

```
<商品名>-lookbook/
├── 00-input/                原始服饰图（唯一未经模型改写的 ground truth）
├── 01-garment-triview/      garment-triview.png
├── 02-plans/                plans.md（全部方案，`---` 分块）
├── 03-shoots/
│   ├── plan-01/             model-triview.png、scenes.md、
│   │                        主图01.png…主图05.png（1:1）、详情图01.png…详情图03.png（3:4）
│   └── … plan-NN/
├── batch.json               临时批装配文件
└── manifest.json            全部产物状态与参考图记录
```

`plan-NN/` 目录出图后即可被 `doudian-publish` 直接读走，不需要中间那道手工改名。主图生成时就是 1:1，所以 `publish.mjs` 的居中裁剪对它是空操作，不会再产生 `主图NN_1x1.jpg`。

**方案与场景提示词各自只有一个文件。** `plans.md` 装全部方案，`plan-NN/scenes.md` 装该方案全部场景，块之间用单独一行 `---` 分隔，块序即编号。不要再生成 `plan-01.md` 或 `scene-1.md` 这类拆分文件——脚本已改为直接解析单文件，两套并存必然出现改了一处忘了另一处。

`scenes.md` 的块号与图的对应关系是**位次映射**：第 1–5 块 → `主图01`–`主图05`，第 6–8 块 → `详情图01`–`详情图03`（按实际 `mains`/`details` 推）。块标题仍写 `## 场景 N`（N 为 1 到 mains+details 的全局序号），04 段提示词原文不动，所以写场景词时不区分主图/详情图分工。

## 编排脚本

确定性的活全部交给 `{baseDir}/scripts/pipeline.ts`（bun 运行），你不要手写 JSON 或手算待办：

```bash
bun {baseDir}/scripts/pipeline.ts init --workspace <ws> --product <名称> [--plans 10] [--mains 5] [--details 3]
bun {baseDir}/scripts/pipeline.ts classify --workspace <ws> --value 套装
bun {baseDir}/scripts/pipeline.ts plan --workspace <ws> --plan 3
bun {baseDir}/scripts/pipeline.ts refs --workspace <ws> --plan 3
bun {baseDir}/scripts/pipeline.ts build-batch --workspace <ws> [--plans-only 1,2] [--quality normal]
bun {baseDir}/scripts/pipeline.ts sync --workspace <ws>
bun {baseDir}/scripts/pipeline.ts mark --workspace <ws> --path <路径> --status failed --error "<原因>"
bun {baseDir}/scripts/pipeline.ts status --workspace <ws>
```

`--ar` / `--scenes` / `--main-ar` / `--detail-ar` 已废弃，传了会报错退出而不是静默忽略：`--ar 3:4` 若被忽略，你会以为全批是竖版，实际前 5 张仍是方图，而这要到几十张图出完才看得出来。

创作性的活（写方案、写场景提示词、判断漂移）由你完成，脚本不碰。

`plan --plan N` 从 `plans.md` 里按 `---` 切出第 N 块原文打印出来，步骤 4、5 需要「该方案的完整内容」时用它，不要每次把整份 `plans.md` 读进上下文。

它会校验块内 `## 方案 N` 的编号与 `--plan` 是否一致，不一致就报错退出。**此时去修 `plans.md` 的编号，不要随手加 `--loose` 绕过。** 编号错位意味着把另一个方案的搭配拿去生成这个方案的图，整组作废，而且要到出图后才能看出来。`build-batch` 与 `status` 也会把全量编号问题作为告警列出。

## 占位符

替换规则只写在这里，`assets/` 里只有提示词原文加占位符。

| 占位符 | 含义 |
|---|---|
| `{{REF_IMAGES}}` | 参考图路径（`02-plan-table.md` 中替换原本的 `@图片1`） |
| `{{PLAN_COUNT}}` | 方案总数，默认 10 |
| `{{PLAN_INDEX}}` | 当前方案序号 |
| `{{SCENE_COUNT}}` | 每方案场景数，等于 `mains + details`，默认 8 |

## 工作流

### 步骤 0 — 建工作区

问清商品名与原始图位置（用户没给就从图片文件名推导商品名）。跑 `init`，把原始图拷进 `00-input/`。

参数默认 `--plans 10 --mains 5 --details 3`。**若用户想先小规模试产，用 `--plans 1 --mains 1 --details 1`**：满配是 1 + 10 + 80 = 91 张图，先花 4 张确认提示词与链路没问题，比中途中断省得多。

### 步骤 1 — 判定品类并落盘

看 `00-input/` 的图，判断是「仅上衣 / 仅下衣 / 套装」，并识别多张图属于哪种情形：

- **同一件衣服的多角度或多细节照** → 全部当参考，合成一张服装三视图
- **多件单品共同构成一套** → 判为「套装」

把结论摆给用户确认，再跑 `classify` 写入。误判成本很具体：套装被判成「仅上衣」，后续每组方案都会擅自补下装。

### 步骤 2 — 生成服装三视图

用 `assets/prompts/01-garment-triview.md` 原文，参考图为 `00-input/` 全部图片，输出 `01-garment-triview/garment-triview.png`。

顺序单发（不走 batch），因为这是全局主参考，需要看清单张结果：

```bash
--ref <00-input 下全部图> --ar 4:3 --quality normal
```

**🚧 硬闸门 ①** — 这张图是后续全部图片的主参考，错了后面全废。给出图片路径，请用户选择：通过 / 重新生成 / 我手动换好了继续。重点让用户核对颜色、版型、图案、细节图那一栏是否可用。

### 步骤 3 — 生成方案

用 `assets/prompts/02-plan-table.md`，替换 `{{REF_IMAGES}}` 为服装三视图路径、`{{PLAN_COUNT}}` 为方案数。这是纯文本推理，不出图。

输出到 `02-plans/plans.md`：全部方案写在这一个文件里，每个方案一块，块之间用单独一行 `---` 分隔。不出表格，不再拆成单方案文件。

**🚧 硬闸门 ②** — 把 `plans.md` 全文直接贴进对话（用户不用开文件就能扫），请用户选择：通过 / 重新生成 / 我改完了继续。这是调转化率的主战场，纯文本改起来最便宜。yolo 模式下贴完即继续。

### 步骤 4 — 每方案生成模特三视图

用 `assets/prompts/03-model-triview.md`，`{{PLAN_INDEX}}` 替换为方案号，并把 `plan --plan N` 取出的该方案完整内容随提示词一并给出。

**模特必须穿着主商品 + 该方案的「新增搭配」（含鞋履、配饰、发型、妆容），是完整 look，不是素模。** 否则方案里最关键的差异化字段要等到最后一层扇出（70 张）才第一次被渲染，等于拿全部额度去赌。

参考图与优先级同步骤 5 的规则（见下），此时尚无模特图，喂 `00-input/` + 服装三视图。顺序单发，`--ar 4:3 --quality normal`（1k），输出 `03-shoots/plan-NN/model-triview.png`。

**🚦 软闸门 ③** — 全部模特三视图出完后停一次，列出路径，让用户多选「哪几组继续跑场景图」，默认全选。用户可以直接跳过这一道，yolo 模式下视为全选。坏方案在这里拦住，就省掉了它对应的全部场景图。

### 步骤 5 — 每方案生成场景提示词

用 `assets/prompts/04-scene-prompts.md`，替换 `{{PLAN_INDEX}}` 与 `{{SCENE_COUNT}}`，并给出 `plan --plan N` 取出的方案内容与模特三视图。纯文本，不出图。

输出到 `03-shoots/plan-NN/scenes.md`：该方案的全部场景写在这一个文件里，每场景一块，块之间用单独一行 `---` 分隔，块序即场景号。不再拆成 `scene-N.md`。

写完跑一次 `status` 核对每方案的「场景词 N/M」计数——块数与 `mains + details` 不符时 `build-batch` 会漏图，此处发现只需重写文本。缺的块若落在后三位，丢掉的就是详情图。

### 步骤 6 — 生成最终展示图

跑 `build-batch` 装配，然后交给 baoyu-image-gen 批量出图：

```bash
bun {baseDir}/scripts/pipeline.ts build-batch --workspace <ws>
# 然后用 baoyu-image-gen 的 --batchfile <ws>/batch.json --jobs 10
```

画幅由 `build-batch` 按位次写进每条任务：前 `mains` 张 `1:1`，后 `details` 张 `3:4`，不可用参数覆盖。质量默认 `normal`（1k），用 `--quality` 覆盖。**质量参数只接受 `normal|2k` 两种预设，`normal` 即 1k 分辨率；传 `1k` 会被 baoyu-image-gen 拒掉。** `build-batch` 已在本地先做一道校验，不致于跑到出图时才报错。

`--jobs 10` 在命令行覆盖即可，**不要修改用户的全局 EXTEND.md** —— 那会影响用户其他所有出图任务。

出图后跑 `sync` 回填状态，再跑 `status` 看总览。

#### 参考图链路与优先级

三张参考同时喂，并在提示词末尾附上优先级声明（`build-batch` 已自动附加，手工单发时你要自己带上）：

| 要保住什么 | 以谁为准 |
|---|---|
| 人物身份、脸型、发型、妆容、鞋履配饰 | 模特三视图 |
| 主商品的颜色、图案、面料质感 | **原始服饰图** |
| 主商品的背面结构与局部细节 | 服装三视图 |

原始图必须在链路里当色彩锚点：模特三视图是第二代产物，它自己已经可能偏了，若以它为唯一真相，全部场景图会继承这个偏差且再无校正源。同时要声明「以上参考图均为同一主商品与同一模特，请保持同一性，不要重新设计或生成相似的新主体」——长篇的五官描述反而会让模型合成一个新的相似人物。

### 步骤 7 — 失败汇总

三级处理：baoyu 自带每图 3 次重试不干预 → 3 次全败则 `mark` 为 failed 并**继续跑其余图**，不中断整批 → 全批结束后 `status` 汇总失败清单，问用户「重试这些 / 跳过 / 停下」。

人工返工入口：用户看到某张漂移了，删掉该文件后跑 `sync`，状态自动退回 pending，重跑 `build-batch` 就会补上。

## 出图参数速查

| 产物 | 方式 | 画幅 | 质量 |
|---|---|---|---|
| 服装三视图 | 顺序单发 | 4:3 | normal（1k）|
| 模特三视图 | 顺序单发 | 4:3 | normal（1k） |
| 主图 `主图NN.png`（前 5 张）| batch `--jobs 10` | 1:1 | normal（1k） |
| 详情图 `详情图NN.png`（后 3 张）| batch `--jobs 10` | 3:4 | normal（1k） |

三视图是横向三联加下方细节，需要横幅；主图对齐抖店轮播位的方图要求；详情图是往下滚的竖版卖点图。

**质量列一律用 baoyu-image-gen 的 `--quality` 合法值**：`normal`（对应 1k 分辨率）或 `2k`。**不要传 `1k`** —— 它不是合法预设，baoyu 会以 `Invalid quality: 1k` 直接报错退出。

## 收尾提醒

三件最容易出错、也最贵的事，换个说法再讲一次：

**提示词原文不要动。** 用户把那四段调顺了才交给你，你的价值在编排和归档。包括其中的「输出格式铁律」——`plans.md` 不出表格、`scenes.md` 单文件 `---` 分块，这两条是脚本解析的前提，改成其他形式 `build-batch` 会直接取不到场景块。

**闸门前不要抢跑。** 服装三视图和方案这两道停下来，是因为它们各自决定了下游 90 张图的命运，而在此处返工只花 1 张图或 0 张图的代价。除非用户明确要 yolo —— 那是用户自己承担这个代价，不是你替他决定。

**原始服饰图始终在参考链里。** 它是唯一没被模型改写过的事实。链式引用本身就会累积漂移，抽掉这个锚点，漂移就变成单向不可逆的。

**「详情图」这个名字只保证文件名与画幅。** 04 段提示词原文不动，它要求 8 张覆盖远景到近景并串成连贯故事板，而 5/3 的切分是在第 5 块处机械截断——落到 6–8 块的是哪几个景别，由写场景词时的排布决定，不受这套命名控制。不要向用户宣称后三张在内容上是「卖点细节图」。

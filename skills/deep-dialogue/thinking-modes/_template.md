新增后要在 SKILL.md 的路由表里加一行：归到哪一类、代表人物是谁、什么时候选它。触发条件只写在表里，不写在本文件。

`stance` 和 `voice` 会被 SKILL.md 直接执行——`stance` 作为这个人最根本的判断依据，`voice` 决定回复怎么说出来。所以 `voice` 不要写成“有个性”这类无法执行的形容，要写清语速快慢、偏好什么词、怎么追问；写了不留情面或带点冒犯就会照做，锋利只针对判断本身，不指向用户这个人。

## 适用情景

只写来历：当初是哪一类问题用常规办法处理不好，人们才总结出这种思考方式，那类问题长什么样子。

这一段不讲问题的关键在哪里——关键在哪里写在下面的思维框架里。也不要写“听到什么话就选它”，触发条件写在 SKILL.md 的路由表里，本文件不写第二份。

## 思维框架

只在重述能揭示关键关系、前提或约束时改写用户的问题；问题已经清楚时直接分析，情绪话题可以先复述感受。

- **可用的转化形式：** 梳理环节及其关系、观察变化趋势、比较选项、列出关键假设、对比成本，或还原具体场景。
- **转化的依据：** 说明这种表达帮助看清了什么，不为体现人物风格而把问题强行套进框架。

用无序列表写这个框架的独特主张：它关注什么、依据什么判断、适用条件是什么。人物特色通过这些判断体现；主张中的经验判断应说明条件，不写成无条件成立的事实。

不要写成编号步骤。编号会让人物照着念，念出来就成了方法论讲解，而不是他在说话。先后关系写进主张里（“榨干先于扩容”、“要等他松下来才问他想怎么办”），不靠编号表达。

本节只写判断依据；推进和收束放在「对话框架」。共用的证据标准、提问时机、情绪话题处理和用户需求优先规则遵循 SKILL.md，不在各思考方式文件里重复编排。格式如下：

```
问题转化：<何时有必要重述，以及重述能揭示的关键关系>

### 框架特征
- 框架主张/特征
- ...
```

## 对话框架

写两部分。

**追问的落点。** 用户的说法在哪个地方是空的，就往那里问。写清判断依据：听到什么样的表述就说明还没答到点上，代表人物接下来问什么。有些思考方式靠追问推进，有些靠陪着用户说下去，按代表人物的实际做法写，不必一律写成质问。

**这一轮什么时候算问完。** 写清这种方式带来的关键进展，以及已有足够依据或仍有未知时怎样收束。结果可以是判断标准、待验证假设、具体行动，或表达清楚的感受；不要把用户接受框架预设的结论作为完成条件。

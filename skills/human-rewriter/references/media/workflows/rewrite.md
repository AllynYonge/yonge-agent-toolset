# 改写工作流

适用于所有改稿任务，包括润色、去 AI 味和按平台改写。`deep low` 的逐段重写以 `references/rework.md` 为底，本文件只补账号、平台、风格、`deep medium/high`、flow 与审核相关的步骤。没有账号配置、没有目标平台或没有配置风格时，对应步骤跳过。

| 条件 | 行为 |
|------|------|
| 未配置 `output_dir` | 仅在对话中输出，不保存文件 |
| 已配置 `output_dir` | 改写完成后，将文件保存至 resolver 返回的 `output_dir`，文件名为 `{title}.md`；有目标平台时，文件内容以 `# {platform}-{medium}-draft` 作为顶级标题标记草稿态，文章标题用二级标题 `## {title}` 紧跟其后；没有目标平台时只写 `# {title}` |
| 文章通过审核正式交付时 | 将分区标题中的 `-draft` 后缀去掉（如 `# xhs-note-draft` → `# xhs-note`） |

`# {platform}-{medium}` 分区标题是文件编排标记，不是正文，check_prose.py 不对它报错。

## 1. 加载偏好设置

在向用户提问之前，存在 EXTEND.md 或带了 `--profile` 时，调用 resolver 获取最小 active profile 配置（路径以 human-rewriter 技能目录为根），否则跳过，合规清单按 `[]` 处理：

```bash
python3 scripts/resolve_preferences.py \
  --workspace-dir "{workspace_dir}" \
  [--profile "<name>"]
```

读取返回的 `compliance_guardrails`，补入本次明确边界，作为改写与审核共用清单；各档位和短任务均适用 `references/media/overview.md`「合规红线」。按 SKILL.md「交互流程 simple 与 detail」的决定顺序确定 flow。

### 2. 确定选题

**simple 流程**：跳过本步。原文的论点就是改写的论点；用户从分析模式带来了方向，就以「选题交接信息」的核心论点为准。

**detail 流程**：将选题任务委派给 `agents/topic-selection.md` 子代理完成。即使用户已从分析模式选定方向，也不跳过，因为分析方向只有灵感与切入策略，还不是可执行选题。

MUST 将选题结果原样呈现给用户，等待选定后注入后续步骤：

- 目标用户与场景 → 补充信息收集中的目标读者
- 内容结构 → 指导正文构建
- 核心论点 → 作为核心论点起点
- 关键词与标签 → 指导标题和 SEO

### 3. 提取语义锚点 / 结构蓝图

本步骤根据 `--deep` 档位执行不同操作：

#### --deep low（默认）：提取语义锚点

按 `references/rework.md`「动手前记下不能改的东西」提取全部锚点，并按同一文件「先圈出已经活着的地方」标出原稿里要保留的部分。以上信息在改写后必须在含义上保持不变。

#### --deep medium：缩减锚点范围

仅保护以下核心事实类锚点：

- 名称、人名、机构名、产品名
- 日期、时间线和事件顺序
- 数字、价格、比例、排名
- 因果主张

以下信息释放为可改动：示例、过渡段落、支撑性论据的具体措辞、对比关系的具体表述方式。允许替换论据、重排段落顺序、增删支撑细节，只要核心事实不变。新增的论据和细节只能来自用户材料或检索到的可核验来源，不补造例子（SKILL.md 第一关）。

#### --deep high：提取结构蓝图

**开放条件**：新内容必须有来处。虚构题材可以按 `references/fiction.md` 创造；现实题材需要用户提供新材料，或者能检索到足够的可核验来源，按 SKILL.md 第一关重新计数。现实题材没有新材料时，不开放 high，改用 low 或 medium，并告诉用户原因。

不提取语义锚点。改为提取原文的**结构蓝图**——逐段标注每段承担的功能角色：

| 段落功能 | 示例 |
|----------|------|
| 开场设问 | 抛出悬念或痛点 |
| 场景铺设 | 建立具体情境 |
| 论点陈述 | 亮出核心主张 |
| 举例论证 | 用案例支撑论点 |
| 数据佐证 | 用数字增强说服力 |
| 转折/递进 | 推进或翻转论证方向 |
| 情感共鸣 | 连接读者感受 |
| 总结收束 | 收尾给出收获或行动 |

提取后形成段落功能序列（如：开场设问 → 场景铺设 → 论点陈述 → 举例论证 × 2 → 转折 → 新论点 → 总结收束）。这个序列是改写的骨架约束——后续步骤 6 用全新内容填充每个功能槽位，但保持序列不变。

同时记录原文的修辞节奏特征（段落长短交替模式、短句密集区与长句舒展区的分布），作为节奏参考。

### 4. 风格

按优先级确定写作风格：

1. 用户本次请求中的显式风格指令（最高优先）
2. resolver 返回的 active profile `custom_style`（内联自定义风格）
3. resolver 返回的 active profile `writing_style`（内置风格预设名）
4. 都没有时不套用预设，按 SKILL.md 的默认写法；原稿自己的声音按 `references/rework.md` 保留

有风格时使用 resolver 返回的 `style` 获取具体声音参数。若用户提供了写作样本要求模仿，或需要从样本提取风格结构，按 `references/media/voice.md` 的自定义风格结构与样本提取流程执行。风格参数命中硬禁令时不执行。

### 5. 平台

从用户信号中确定目标平台：

| 信号 | 平台 |
|------|------|
| 公众号/微信/长文/深度 | 微信 |
| 小红书/xhs/笔记/种草 | 小红书 |
| 无信号 | resolver 返回的 active profile `platform`，再无则没有目标平台，跳过本步与 5.5，后续步骤里的平台形态约束一律不套用 |

确定后按 `references/media/platforms/{platform}-{medium}.md` 应用发布形态约束（分发机制、用户心智、内容规范中的段落密度、交互偏好中的 emoji 策略等）。

### 5.5 媒介

在平台确定后、改写开始前确定内容媒介（载体）。媒介决定叙事结构、开篇钩子、篇幅特性。

| 信号 | 媒介 |
|------|------|
| 长文/深度/专栏文章 | article（长图文） |
| 短图文/卡片/笔记/种草 | note（短图文笔记） |
| 无信号 | resolver 返回的 active profile `medium`，再无则按平台推断（微信→article，小红书→note） |

确定后从 `references/media/platforms/{platform}-{medium}.md` 加载完整形态约束（叙事结构、开篇钩子、篇幅特性、起草侧重、结构步）。篇幅特性与 `length` 硬约束冲突时，以 `length` 为准。形态特定的起草侧重与可选结构步由该数据文件的 §起草侧重 / §结构步 供料，改写阶段就地读取——新增或调整某个形态的行为只改它的数据文件，不改本流程。

### 6. 改写

动手前读取 `references/rework.md`。先逐条核对 `compliance_guardrails` 与原文标题、主张、例子和行动建议。若修复需要删除受保护信息或改变立场，先列出冲突原文、规则与可选方向，等待确认；不为合规伪造来源，也不只换词掩盖原有功效暗示。

本步骤根据 `--deep` 档位执行不同策略：

有目标平台时，开始改写前把 `references/media/platforms/{platform}-{medium}.md` §起草侧重 叠加到本步策略之上（该形态的侧重优先于通用倾向，但不越过锚点保护与 `length` 等硬约束）；并读取该文件 §结构步——非空则按其说明补做这一步并入改写规划，为空则跳过（基础流程预留的扩展槽，新增特殊结构需求的形态时只填数据文件本节，不改本流程）。

#### --deep low / medium：逐段重写

按 `references/rework.md`「逐段重写」执行。读完一段，用一句话说出它想表达什么，然后不看原文按这句话重新写，写完对照锚点清单（`low` 对照全部锚点；`medium` 仅对照核心事实锚点）。

在此之上叠加两件事：

- 有目标平台时，叠加平台形态的起草侧重，比如小红书笔记要重点前置、单点聚焦。
- `medium` 允许替换论据和示例，但新内容只能来自用户材料或可核验来源。

原稿的材料撑不住原来的篇幅时，按 `references/rework.md`「材料撑不住原来的篇幅」删短，不补造例子。

#### --deep high：结构复刻

在步骤 3 中已提取原文的段落功能序列和修辞节奏特征。本步骤以该结构蓝图为骨架，用全新内容填充每个功能槽位。

执行方式：
1. 逐个功能槽位创作：按段落功能序列依次填充，每个槽位产出对应功能的新段落
2. 内容来源：步骤 2 选定的方向（simple 流程为原文论点）提供核心论点和切入角度。新的论据、案例和数据只能取自用户材料、检索到的可核验来源，或虚构题材中按 `references/fiction.md` 创造的内容。某个功能槽位没有材料可填，就合并或删掉这个槽位，不编造
3. 节奏参考：参照原文的修辞节奏特征（段落长短交替、句式密度变化），但不拘泥于精确复制
4. 不对照原文内容：原文的具体事实、例子、数据全部可替换——约束对象是结构，不是语义

注意事项：
- 结构蓝图是指导而非牢笼——如果某个功能槽位在新论点下显得多余或不自然，可以合并相邻槽位或微调功能，但整体叙事节奏应与原文同构
- 如果用户同时指定了具体的语义保护要求（如"数据不要动"），在对应槽位中保留该内容

#### 长内容跨节一致性

对于长内容（超过 long_threshold）：按标题或主题段落逐块处理。每完成一个段落后执行跨节一致性检查：

1. 回读前一节最后两句 + 当前节开头两句，检查语气温度是否断裂（如前节冷静分析，当节突然煽情）。
2. 对比当前节与前一节的句式节奏——如果两节的平均句长和段落长度近似，主动打破其中一节的节奏。
3. 检查用词重复：如果同一个"过渡词"或"态度词"在相邻两节都出现，替换其中一处。
4. 全部段落完成后，快速通读首段和末段，确认全文的情感弧线连贯（起点 → 终点之间有推进，而非平行重复）。

### 7. 改稿与确定性检查

改写完成后，按 `references/revision.md` 过一遍，再按当前合规清单逐条检查；待核实或需用户决定的冲突按 `references/media/overview.md`「合规红线」处理。

然后 MUST 运行合并后的检查脚本，一次覆盖硬禁令、篇幅与规避词。脚本不能替代合规语义审核：

```bash
python3 scripts/check_prose.py "{article_path}" \
  {constraint_check_args} \
  [--platform-labels] \
  --json
```

`{constraint_check_args}` 取 resolver 返回的同名字段，没有运行 resolver 时省略。

**执行规则**：
- 硬禁令失败：找到它原本想说的事实，用普通句子说出来。
- 篇幅超过上限：一次性判断需要删减多少字，从全文中定位 1-3 处可精简的段落或句子，集中删减，不逐字微调。优先删减冗余解释、重复论证、可合并的相邻段落。
- 篇幅低于下限只是提醒：不补字，交稿时说明实际字数。
- 规避词命中：用具体动作或事物替代包装性词汇。
- 修复后重新运行脚本，失败项清零后再进入步骤 8。
- 连续 3 次修复仍未通过，向用户说明当前状态（失败项、实际字数、目标区间、难以修复的原因），请用户决定。

### 8. 交稿

**simple 流程**：只交改写稿。合规清单非空时，先完成步骤 9 再交；清单为空时直接交。原稿删掉三分之一以上时，按 `references/rework.md` 告诉用户删了哪几块。

**detail 流程**：暂停委派审核子代理，先向用户呈现以下内容：

1. **完整改写稿**（或指明已保存的文件路径）
2. **优化建议**（2-4 条）：基于当前稿件，给出主代理观察到的可选改进方向（如某段论证可以更具体、某处过渡略突兀、结尾可以更锋利等）。标记为建议，不自动执行。

**等待用户回复**：
- 用户确认"可以"/"没问题"/"继续" → 进入步骤 9
- 用户提出修改意见 → 执行修改后重新呈现，再次等待确认
- 用户采纳部分优化建议 → 执行对应建议后重新呈现

### 9. 审核

| flow | 合规清单 | 行为 |
|------|------|------|
| simple | 空 | 跳过 |
| simple | 非空 | 在后台执行 `agents/article-review.md` 一轮，只处理合规红线结论；能自主修复就修，修完重跑步骤 7，不派第二轮；不能自主修复的列入待确认清单随稿交付，稿子不标为可发布 |
| detail | 任意 | 执行 `agents/article-review.md`，传入目标平台（没有时传文体）和当前完整 `compliance_guardrails` 清单（无额外规则时传 `[]`），调度遵循其中的「调度规则」。修复→再审循环按「主代理闭环」，直到满足终止条件 |
